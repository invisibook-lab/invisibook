# Proof of Buy

一种为 Layer1 设计的 Layer2 共识协议。

## 1. 概述

Proof of Buy（PoB）用**在 L1 上真实花掉的钱**代替**在 L2 上锁仓的币**来购买 L2 的
出块权，用 VRF 对支付金额做随机加权决定每一高度的胜者，再把区块头与竞选得分锚回
L1，由 L1 的最终性给 L2 定序和定终局。

它属于 PoW 一系：出块有不可撤销的真实成本，共识结果客观可验证，不需要任何主观投票。
与合并挖矿的区别在于，PoB 复用的是已经凝结成 L1 代币的**过去算力**，而不是 L1 的
实时算力，因此不会把 L1 矿工的算力变成对 L2 的攻击面。

## 2. 前提与适用范围

PoB 的安全性完全建立在 L1 账本安全之上。L1 账本一旦出现漏洞，漏洞会直接蔓延到 L2。
因此 L1 的选择受两个条件约束：

- **L1 必须是 PoW 公链**。PoB 的客观性来自成本的不可撤销，这要求底层账本本身也建立
  在不可撤销的成本之上。
- **L1 必须具备足够的脚本能力**。分叉裁定发生在 L1 侧，L1 需要能够表达"比较得分并
  选出主分支"这一逻辑。脚本能力受限的 L1（如比特币）无法承载 PoB 的最终共识。

CKB 同时满足这两点，且其设计定位本身即为 L2 服务，是 PoB 最自然的宿主链。但 PoB 是
通用协议，并不排斥其他满足上述条件的 L1。

本文其余部分以 CKB 为 L1、以垂直领域应用链为 L2 展开。

## 3. 术语

| 术语 | 含义 |
| --- | --- |
| L1 / 母链 | 提供账本安全、最终性与脚本能力的底层公链 |
| L2 / 子链 | 挂载在 L1 上的应用链，使用 PoB 达成共识 |
| mining addr | L2 在 L1 上的收款地址，矿工的出块支付流入此处 |
| `payment` | 矿工为某个 L2 高度声明支付的 L1 代币数量，以密文承诺形式提交 |
| `vrf_output` | 矿工用出块私钥对确定输入求值得到的 VRF 输出 |
| `goal` | 出块竞选得分，`goal = f(payment, vrf_output)` |

## 4. 协议结构

PoB 由三层构成，各自解决一个独立的问题：

```
┌──────────────────────────────────────────────────────────────────┐
│  准入      谁有资格成为矿工                                        │
│            持有 L1 原生代币即可参与，无链上注册表                    │
├──────────────────────────────────────────────────────────────────┤
│  出块      某一高度由谁出块                                        │
│            goal = f(payment, vrf_output)，取 max(goal)            │
├──────────────────────────────────────────────────────────────────┤
│  最终      哪条分叉是主链，何时不可回滚                             │
│            (header, goal) 锚定至 L1，L1 裁定并赋予终局性            │
└──────────────────────────────────────────────────────────────────┘
```

## 5. 准入

持有 L1 原生代币是参与共识的唯一门槛。协议不维护矿工注册表，也不定义链上委托逻辑
——散户将代币委托给某个矿工是现实世界中的组织行为，不构成协议组件。

保持准入层为空是刻意的：任何链上白名单或委托合约都会引入需要治理的状态，而 PoB 的
安全性来自支付本身，不来自身份。

## 6. 出块共识

### 6.1 竞选规则

每个高度的出块权归 `goal` 最大者：

```
goal = f(payment, vrf_output)
```

`payment` 是矿工在 L1 上为该高度声明支付的代币数量，`vrf_output` 是矿工用自己的出块
私钥对上一区块哈希求值的结果。两者相乘即为最简形式的 `f`。

**支付的作用是引入成本。** 出块必须有成本，这是共识可被客观验证的前提：攻击者想要
攻击 L2，必须付出与诚实矿工同等的真金白银，而不是像 PoS 那样 nothing at stake。
更重要的是，成本是不可撤销的**支出**而非锁仓——攻击者哪怕筹码最厚，每攻击一次筹码
就减少一次，无法在每个高度都维持同等的出块权重。

**支付同时构筑了规模中心。** 公链需要一定程度的可伸缩中心化，矿池、矿场、质押代理
都在扮演这一角色。若出块节点数以千万计，叔块与孤块会大量涌现，51% 攻击成本反而降低，
网络也会陷入拥堵。PoB 用"愿意付费"这一行为天然筛选出这个规模中心，且这个中心是流动
的，不依赖任何注册或许可。

**VRF 的作用是防止富者垄断。** 若仅按支付金额排序，出块权将稳定归于资金最厚者。
引入 VRF 后，得分被伪随机数加权，短期垄断被显著削弱。VRF 提供三个必要性质：输出对
他人不可预测，因此出块结果不可预测；输出对固定的密钥与输入唯一确定，因此矿工无法
反复试算以求更优结果；验证廉价，因此全网可即时校验。

### 6.2 身份绑定

VRF 密钥必须就是出块密钥，验证时使用区块自带的出块公钥而非独立的 VRF 公钥。同一把
密钥同时承担三个角色：签发 L2 区块、生成 VRF 输出、持有 L1 上的支付账户。

这条约束一次性封死两类作弊：矿工无法生成大量一次性 VRF 密钥来筛选有利输出，也无法
把他人的支付记录挪用到自己的区块上。

### 6.3 出块流程

```
  矿工本地                              全网
  ────────                              ────
  1. 读取本高度已在 L1 承诺的 payment
  2. vrf = VRF(sk, prev_block_hash)
  3. goal = f(payment, vrf)
  4. 打包交易，组装区块
     区块携带 (vrf_output, vrf_proof,
              payment 承诺, 分配证明, goal)
  5. 广播 ───────────────────────────▶  6. 收到候选区块，逐项校验：
                                           · VRF 证明对出块公钥成立
                                           · 支付身份与出块身份一致
                                           · 分配证明成立
                                           · 重算 goal
                                        7. 本高度采纳 max(goal) 的区块
```

## 7. 支付层

### 7.1 出块间隔错配问题

L2 的出块间隔通常短于 L1。若矿工在竞选前才向 L1 发起支付交易，该交易在 L2 出块时尚未
上链，L2 无从得知谁付得更多。这个问题若不解决，L2 的出块间隔将被 L1 绑死，最终只能
退回 PoS 加 BFT 的路线。

### 7.2 预支付与额度分配

PoB 采用预支付加零知识分配证明：

```
  周期开始   矿工向 mining addr 支付一笔 L1 代币，数量为密文承诺 A
                                │
  每次出块   声明本块使用的额度 a_h（无需在 L2 上真实支付，钱已在 L1）
             并给出零知识证明：a_0 + a_1 + ... + a_h ≤ A
                                │
  全网验证   以 L1 上的 A 为公开输入验证该证明
             通过后将 (vrf_output, a_h) 代入计算 goal
```

**额度必须是密文。** 明文预支付会把矿工的资金筹码提前暴露给竞争者，使其得以据此调整
策略。零知识证明让全网相信"所有声明之和未超出实际支付"，同时不泄露 `A` 与 `a_h` 的
具体数值。

### 7.3 支付时点必须前移

如果允许矿工在看到他人得分之后再决定自己支付多少，后广播者将获得天然优势：所有人都
会拖延广播，先观察别人的 `goal`，再反推自己需要支付多少才能反超。共识会因此退化。

正确的时序是：**先在 L1 上以密文承诺声明本高度的支付额，之后才计算 VRF。**

```
  ✗  计算 VRF → 观察他人 goal → 反推支付额 → 广播
  ✓  L1 承诺支付额 → 计算 VRF → 计算 goal → 广播
```

在这一时序下，`payment` 在看到任何竞争信息之前就已锁定，`vrf_output` 对固定输入唯一
确定，两个输入均不可调整，竞选结果因而既公平又随机。

**前移的幅度约为 4 分钟，即 24 个 L1 区块。** 这一数值由自私挖矿的防御需求决定，
见 9.3。

## 8. 最终共识

### 8.1 锚定与裁定

每个 L2 区块的头部与其 `goal` 一并提交至 L1。同一 L2 高度可能有多条分叉被不同矿工
提交，裁定规则是：**在这些分叉中选择 `max(goal)` 的一条作为主分支。**

`goal` 中的 VRF 输出难以伪造，且每一次出块都有真实的 L1 支付作背书，因此它是一个
客观可验证的数值。任何人只需比较 `goal` 即可确定应当跟随哪条分叉，无需投票，也无需
额外的通信轮次。

承载这批数据的 L1 区块一旦出块完成，被选中的 L2 主分支即视为 finalized，不可回滚。

```
  L1:  |———— block N ————|———— block N+1 ————|———— block N+2 ————|
                          ▲                    ▲
                          │                    │
  L2:  |h |h+1|h+2|h+3|h+4|h+5|h+6|h+7|h+8|h+9|h+10|
        └── 这批区块的 (header, goal) 落在 N+1 上 ──┘
                          │
                          └─ N+1 出块 → 该批 L2 区块的主分支被一次性 finalize
```

### 8.2 分工

裁定发生在 L1 侧，由 L1 合约执行。L2 节点的职责是提交与跟随：把 `(header, goal)`
写上 L1，再读回被锚定的规范链，若本地链与之不一致则回滚并切换。L2 不实现自己的分叉
选择算法。

这一分工使 L2 无需处理分叉裁定中最棘手的部分，也避免了 L1 与 L2 两套选择规则之间可能
出现的不一致。

### 8.3 锚定的长期意义

协议长期运行后，mining addr 会累积可观的 L1 代币。若其控制者将来积累到足以颠覆该链的
筹码，理论上存在重写历史的可能。把 finalized 的主链持续锚定在 L1 上，等于把已发生的
历史钉死在一条安全性更高的链上，使任何长程攻击都无法生效。这是协议对自身未来的约束。

### 8.4 不引入 BFT

BFT 的本质是以主观投票决定终局。只有在出块无成本、缺乏客观约束的体系中，才必须依靠
人为投票来完成分叉选择。PoB 中的 L1 支付是巨大且客观的成本约束，矿工可直接据此分辨
主链，此时叠加 BFT 属于冗余，只会引入更高的网络复杂度与工程复杂度。

若特定场景需要更短的确认时间，可通过约定更激进的终局规则实现，例如取最先达到三个
区块的分叉的 `max(goal)` 为主分支并立即标记为 finalized，而无需引入投票。

## 9. 攻击面与防御

### 9.1 富者垄断

单纯按支付金额竞选会让资金最厚者稳定获得出块权。VRF 加权使得金额优势只能转化为概率
优势，无法转化为确定性优势。

### 9.2 后广播优势

见 7.3。支付承诺前移使竞争双方的输入在互相观察之前即已锁定。

### 9.3 自私挖矿

在 L2 上直接自私挖矿不成立：决定出块的只有 VRF 输出与支付额，前者对矿工自身唯一确定，
后者已在 L1 上锁定，没有可以隐藏并择机释放的算力。

攻击只能从 L1 发起。同一 L1 高度上可能同时存在两个区块，攻击者在两条 L1 分叉上同时为
同一个 L2 高度提交支付承诺。在 L1 分叉收敛之前无人能确定哪条会成为 L1 主链，L1 最终性
的不确定会传染给 L2 的最终性。

将支付承诺前移 24 个 L1 区块（约 4 分钟）即可消除这一窗口：该深度已能提供足够的概率
确定性，L2 在使用某笔承诺时，其所在的 L1 分叉早已收敛。

### 9.4 项目方的女巫攻击

mining addr 持续吸纳矿工支付的代币，这使 L2 项目方处于一个特殊位置：它若亲自参与挖矿，
支付的对象是自己，除 L1 手续费外没有实际成本，而其他矿工仍在向它输送代币。

VRF 只能保证金额多不必然中选，却挡不住女巫攻击：项目方可以化身数千个矿工同时参与竞选，
把诚实矿工的中选概率无限稀释。

防御方式是给流出 mining addr 的代币打上不可逆标记：

```
     矿工支付 ──────────▶  mining addr
                                │
                    转出时在脚本中写入约束：
                    这些代币永远不可再回到 mining addr
                                │
              ┌─────────────────┴─────────────────┐
              ▼                                   ▼
      可用于开发、运营、生态资助          无法再用于为自己的链挖矿
```

该约束写死在代币的类型脚本中，项目方无法通过混币等抹除交易历史的手段绕过。唯一的迂回
路径是拿被标记的代币去市场上兑换普通代币，但被标记代币用途受限，兑换率普遍高于一比一，
项目方需付出超量代币才能换回可用于攻击的部分，这不可持续。且 L2 越有价值，兑换率越高，
攻击成本越大。

### 9.5 长程攻击

见 8.3。已锚定至 L1 的历史不可回滚。

## 10. 经济模型

### 10.1 代币不销毁

一种直觉的做法是把矿工支付的 L1 代币直接销毁以制造通缩。PoB 不这样做，因为协议的目标
是让大量应用链可以作为 L2 长期挂载在 L1 上，销毁在这个尺度上会产生三个后果：

- 当销毁速度超过 L1 增发速度，本质是在消灭 L1 的财富，L1 将面临流动性枯竭。
- 当销毁速度不超过增发速度，本质是再分配，那就必须回答增发出来的代币应当归谁——而把
  代币直接转给一个固定地址本身就是这种再分配的一个特例。
- 通缩推高币价后，持币者愈发不愿把代币投入 L2 挖矿，L2 的共识安全成本反而持续下降。

因此代币流向 L2 项目方，且不会被永久锁定：它们是流动的，用于覆盖 L2 的开发与运营成本。
由此产生的作恶激励由 9.4 的机制约束。

### 10.2 出块奖励

竞选失败的矿工同样获得一定额度的 L2 原生代币作为补偿，类似于对叔块出块者的补偿。参与
竞选因此不是"赢者通吃、输者归零"的零和博弈。

### 10.3 价值循环

```
        L2 应用价值提升
              │
              ▼
   L2 手续费收入提高，原生代币更有价值
              │
              ▼
   更多 L1 持币者愿意支付代币成为 L2 矿工
              │
              ▼
   L1 代币买压增加，L1 代币更有价值
              │
              └──────────▶ （回到起点）

   反向亦成立：L2 无价值 → 原生代币无价值 → 无人愿意投入 → 自然出清
```

PoB 因此不是对 L1 的抽血，而是把 L2 的应用价值反向传导回 L1 的通道。

### 10.4 与 PoS 的结构性差异

**成本结构。** PoS 的启动成本极低，牛市早期易于低成本推高币价，但下跌之后信用与价格
极难恢复，且拉盘严重依赖交易所与做市商。PoB 的成本是真实且不可撤销的支出，安全性不随
币价短期波动而成倍衰减，也不会被 restaking 一类的衍生协议透支。

**分发路径。** 传统 PoS 中，项目方发币，用户在交易所买入，再质押锁仓——中间被交易所
两次抽成，项目方拿不到足够现金流，用户持有的是缺乏流动性的资产并持续承担跌价风险。
PoB 中矿工与项目方直接建立联系，资金直达项目方，而矿工获得的 L2 原生代币是完全流动的，
可立即用于任何用途。

**共识客观性。** PoS 需要配合 BFT 类协议完成分叉选择，而 BFT 投票不是客观可验证的
共识，工程复杂度与网络传播复杂度均高。PoB 的分叉选择是对一个数值的比较。

## 11. 区块生命周期

```
  [PRE-COMMITTED]  支付承诺已在 L1 上完成，且已积累 24 个 L1 区块确认
         │
         ▼
  [PROPOSED]       计算 VRF 与 goal，组装区块并广播
         │
         ▼
  [VERIFIED]       全网校验 VRF 证明、身份绑定、额度分配证明，重算 goal
         │
         ▼
  [ADOPTED]        本地采纳 max(goal) 的区块，执行交易并落库
         │
         ▼
  [ANCHORED]       (header, goal) 提交至 L1，同高度多个分叉在 L1 上竞争
         │
         ▼
  [FINALIZED]      L1 裁定 max(goal) 且承载区块出块完成，该分支不可回滚
         │
         ▼
  [FOLLOWED]       L2 读回裁定结果，本地链若不一致则回滚并切换
```

## 12. 开放问题

- **L1 与 L2 同时回滚。** L1 与 L2 均为中本聪共识，两者同时发生重组的极端情况下，
  跟随规则的表达需要进一步细化。
- **确认延迟。** 中本聪共识的终局延迟对低延迟场景构成限制。8.4 给出的短周期终局规则
  是一个方向，其安全边界尚待量化。
- **`f` 的具体形式。** 乘法是最简形式，是否存在更能抵抗金额优势的加权函数值得探索。
