## 0. 一句话概括

**PoB 用「在 L1 上真实花掉的钱」代替「在 L2 上锁仓的币」来购买 L2 的出块权，
再用 VRF 对支付金额做随机加权，最后把 (区块头, goal) 锚回 L1，由 L1 的最终性
来给 L2 定序和定终局。**

它在哲学上属于 PoW 一系（出块有不可撤销的真实成本、共识客观可验证），而不是
PoS 一系（锁仓、主观投票）。janx 在 #13 的类比最准确：PoB 类似合并挖矿，但它
复用的是**已经凝结成 L1 代币的「过去算力」**，而不是 L1 的实时算力，因此避开了
合并挖矿被 L1 矿工算力反噬的问题。

## 1. 名词与前提假设

| 名词 | 含义 |
| --- | --- |
| L1 / 母链 | CKB。提供账本安全、最终性、脚本能力 |
| L2 / 子链 | 挂在 L1 上的垂直领域应用链（Invisibook 即订单簿 appchain） |
| mining addr | L2 项目方在 L1 上的收款地址，矿工的出块支付都打到这里 |
| goal | 出块竞选的得分，`goal = f(L1_payment, vrf_output)`（#30） |
| L1_payment | 本区块矿工声明支付的 L1 代币数量（密文承诺形式） |
| vrf_output | 矿工用自己的出块私钥对确定输入求值得到的 VRF 输出 |

**信任假设（#3、#25）**：PoB 的安全性完全建立在 L1 账本安全之上。L1 的账本一旦
有漏洞，漏洞会直接蔓延到 L2。因此可选的 L1 实质上只有 PoW 公链；同时 L1 必须有
足够的脚本能力（BTC 脚本不图灵完备，无法在 L1 侧做 fork choice，所以 BTC 不行）。
CKB 同时满足「PoW + 强脚本 + 天生为 L2 服务」，所以 PoB 最适合 CKB —— 但并非只能
在 CKB 上做。

## 2. 三层共识总览

PoB 分三层，各自解决一个不同的问题：

```
┌──────────────────────────────────────────────────────────────────────┐
│  ① 准入共识 (Admission)    谁有资格当矿工                             │
│     持有 L1 原生代币即可参与；委托关系由矿工在现实世界自行组织          │
├──────────────────────────────────────────────────────────────────────┤
│  ② 出块共识 (Block Production)   这一个高度由谁出块                    │
│     goal = f(L1_payment, vrf_output)，max(goal) 者胜                  │
├──────────────────────────────────────────────────────────────────────┤
│  ③ 最终共识 (Finality / Fork Choice)   哪条分叉是主链，何时不可回滚     │
│     (header, goal) 上传 L1；L1 侧按 max(goal) 选主链；L1 出块即终局    │
└──────────────────────────────────────────────────────────────────────┘
```

> **Invisibook 的取舍**：①在协议层不落任何代码 —— 没有链上矿工注册表，也没有
> 链上 delegation 逻辑，准入和委托是矿工在现实世界自己完成的事。③的**选择规则
> 在 CKB 侧执行**，L2 只负责「提交 + 跟随」，不实现 fork-choice 算法。

## 3. 主流程（正常出块一轮）

```
                      ┌───────────────────────── L1 (CKB) ─────────────────────────┐
                      │                                                            │
  T-4min              │  [1] 矿工提交「为 L2 高度 h 支付 a_h」的承诺 Commit(a_h)     │
  (24 CKB blocks)     │      → 打到 mining addr / 从预付款 A 中划拨                  │
                      │                          │                                 │
                      │                    ≥24 块确认                               │
                      │                          ▼                                 │
  ─────────────────────────────────────────────────────────────────────────────────
                      ┌───────────────────────── L2 ───────────────────────────────┐
  L2 高度 h 开始       │  [2] 矿工本地算 vrf = VRF_sk(prev_block_hash)               │
                      │  [3] goal = f(a_h, vrf)                                    │
                      │  [4] 打包交易 → 组装区块 → 附上 (vrf, proof, a_h, zk, goal) │
                      │  [5] P2P 广播区块                                           │
                      │  [6] 收到别人的区块：验 VRF proof → 验支付与出块身份绑定     │
                      │      → 验 a_h 的 zk 分配证明 → 重算 goal                     │
                      │  [7] 本高度采纳 max(goal) 的那个区块，执行并落库             │
                      └────────────────────────────────────────────────────────────┘
                                                 │
                                        (header, goal) 上传
                                                 ▼
                      ┌───────────────────────── L1 (CKB) ─────────────────────────┐
                      │  [8] 同一 L2 高度可能有多个 fork 被上传                       │
                      │  [9] L1 合约按 max(goal) 选出主分支                           │
                      │ [10] 该 L1 区块一旦出块 → 对应 L2 主分支 finalized，不可回滚  │
                      └────────────────────────────────────────────────────────────┘
                                                 │
                                          L2 读回锚定结果
                                                 ▼
                            L2 节点作为 L1 follower：与 L1 结论不一致则回滚/切换
```

时间轴视角（假设 L1 出块 10s、L2 出块 3s）：

```
L1:   |———— block N ————|———— block N+1 ————|———— block N+2 ————|
                        ^                    ^
                        |                    |
L2:   |h|h+1|h+2|h+3|h+4|h+5|h+6|h+7|h+8|h+9|h+10|...
       └──── 这 3~4 个 L2 区块的 (header,goal) 落在 L1 block N+1 上 ────┘
                        └─ N+1 出块时，这批 L2 区块的主分支被一次性 finalize
```

## 4. 每一步为什么这么做

### 4.1 为什么出块要在 L1 上真实付钱（#1）

- **出块必须有成本**，这是让最终共识可以**客观验证**的前提。攻击者想攻击 L2，
  必须付出同等真金白银，而不是像 PoS 那样 nothing at stake。
- 成本是**不可撤销的支出**而非锁仓：攻击者哪怕筹码最厚，每攻击一次筹码就少一次，
  他无法在每个高度都维持同等比重的出块权。
- 它同时充当了「**规模中心**」。公链需要一定程度的可伸缩中心化（矿池、矿场、质押
  代理都是这个角色）。如果出块节点数以千万计，叔块孤块会暴涨，51% 攻击成本反而
  降低、网络也会拥堵。PoB 用「愿意花钱」这件事天然筛出了这个规模中心。

### 4.2 为什么要 VRF 加权（#1、#30）

只按支付金额排序 = 富者恒赢。引入 VRF 后：

```
goal = f(L1_payment, vrf_output)      # 实现中取 f = 乘法
```

- VRF 输出是伪随机的，且**别人不可预测**，所以出块结果不可预测；
- VRF 输出对同一 (私钥, 输入) 是**唯一确定**的，矿工不能反复试算（不可 grinding）；
- 削弱了富者在短期内绝对垄断出块权的能力。

> 早期帖子（英文版 #1）写的是 VDF，理由是 VDF 抗并行、可防止矿场化。后续方案
> 定稿为 **VRF**（中文主贴已修订，代码也在 commit `4a97006` 完成 `vdf -> vrf`）。
> 原因是这里真正需要的性质是「不可预测 + 唯一确定 + 可快速验证 + 绑定身份」，
> VRF 直接提供，且无需承担 VDF 的串行计算延迟。

### 4.3 VRF 密钥为什么必须就是出块密钥

代码注释里写明了这条（`chain/consensus/vrf.go`）：VRF 走
`ECVRF-SECP256K1-SHA256-TAI`，与 yu 的出块签名密钥、CKB 的支付密钥同曲线，
**一把密钥三种身份**。验证时不使用自带的 VRF 公钥，而是用区块的 `MinerPubkey`：

- 矿工无法生成一堆一次性 VRF 密钥去 grinding 出一个好输出；
- 矿工无法冒领别人的支付（支付方公钥必须等于出块方公钥）；
- 该压缩公钥的 blake160 正好就是 CKB lock args，天然对上 L1 的付款地址。

### 4.4 为什么需要「预支付」：L2 比 L1 快怎么办（#28）

问题：L2 出块 3s、L1 出块 10s。矿工为高度 100 发起的 L1 支付交易还没上 L1，
L2 的第 100 块已经出了 —— L2 此刻看不到谁付得多。**若不解决，L2 出块间隔将被
L1 出块间隔绑死**，最终只能退回 PoS + BFT（如 Stacks 的 PoX）。

PoB 的解法是**预支付 + zk 分配证明**：

```
创世/周期开始:  矿工向 mining addr 支付一笔 L1 token，数量为密文承诺  A
                                         │
出块 h=0..n:    每块声明本块愿意支付的额度 a_h（不在 L2 上真付，钱已在 L1）
                同时给出 zk proof:   a_0 + a_1 + ... + a_n  ≤  A
                                         │
其他矿工:       用 L1 上的 A 验证 zk proof → 通过后把 (vrf_output, a_h) 代入
                计算 goal，得出该高度的赢家
```

- **为什么额度是密文**：明文预支付会把自己的资金筹码提前暴露给其他矿工，他们
  可以据此调整策略（#18 已经指出这一点不舒服）。
- **为什么要 zk**：既要让别人相信「你这些声明加起来没超过你实际付过的钱」，
  又不能泄露 A 和 a_h 的具体数值。

> **注意**：#18 曾提到 Fiber（闪电网络）是短出块间隔场景下的一个自然选项。
> **Invisibook 的实现明确不走 Fiber 这条路**，短出块间隔的支付问题一律用本节的
> 「预支付 + zk 分配证明」解决。

### 4.5 为什么支付要「时间上前移」且必须是承诺（#31）

如果允许矿工先看到别人的 goal 再决定自己付多少，就会出现**后广播者天然占优**：

```
❌ 错误时序:  算 VRF → 等着看别人的 goal → 反推我需要付多少才能反超 → 广播
              结果：所有人都拖到最后广播，共识退化
✅ 正确时序:  先在 L1 上以密文承诺声明「我为高度 h 付 a_h」→ 之后才算 VRF → 广播
              结果：a_h 无法根据别人的 goal 调整；VRF 输出对固定输入唯一确定，
                    也无法调整。goal 因此既公平又随机
```

**提前多久？约 4 分钟（24 个 CKB 区块）。** 理由是防**自私挖矿**：

- 在 L2 上直接自私挖矿基本不可能，因为决定出块的只有 VRF 输出（对自己唯一确定）
  和支付额，没有可藏的算力；
- 攻击只能从 L1 发起：同一 L1 高度上可能同时存在两个区块 A、B，攻击者在两条 L1
  分叉上同时为同一个 L2 高度预支付。在 L1 分叉未收敛前，谁也不知道哪条会成为
  CKB 主链，L1 的最终性不确定就会传染给 L2 的最终性；
- 24 个 CKB 区块（≈4 分钟）已经能提供足够的概率确定性，所以把预支付时点前移
  24 个 slot 是最安全的做法。

### 4.6 为什么 fork choice 放在 L1、用 max(goal)（#30）

L2 每个高度可能有多个 fork 被不同矿工上传到 L1。选择规则很简单：

**在这些 fork 中选 `max(goal)` 的那条作为主分支。**

- `goal` 里的 VRF 输出难以伪造，且每一次出块都有真实的 L1 支付成本作背书，
  所以这是一个**客观可验证**的数值，任何人只看 goal 就知道该跟随哪条分叉；
- 一旦承载这批 (header, goal) 的 L1 区块出块完成，被选中的 L2 主分支**自动视为
  finalized 且不可回滚** —— 后续所有针对该 L2 的长程攻击都失效。

**为什么要把区块数据/头压缩上传 L1（#1）**：协议长期运行后 mining addr 会累积
大量 L1 代币，若其控制者将来积累到足以颠覆该链的筹码，理论上可以回滚历史。把
finalized 的主链锚在 L1 上，就把历史钉死了，这是对未来的自我约束。

> **Invisibook 的取舍**：`max(goal)` 的仲裁由 **CKB 侧合约**执行。L2 节点要写的
> 是 **L1 follower**（读回 L1 锚定的 canonical 链，据此回滚/切换），而不是一套
> 自己的 fork-choice 算法。

### 4.7 为什么不需要 BFT（#16）

- BFT 的本质是**主观投票**决定 finalize。只有在「出块无成本、缺乏强客观约束」的
  体系里（即 PoS），才必须靠人为主观投票来做 fork choice；
- PoB 与 PoW 同构，`L1 token 支付`是巨大的、客观的成本约束，矿工可以直接据此
  分辨主链。此时再叠 BFT 属于画蛇添足；
- 想缩短确认时间不必引入 BFT，可以按场景约定更短的 finalize 规则，例如「最先达到
  3 个区块的那条 fork 的 max(VRF × payment) 即为主分支并标记 finalized」。

> 对照观点（#13，janx）：因为 L1/L2 都是中本聪共识，极端情况（L1、L2 同时 rollback）
> 下 fork choice 会比较复杂，需要仔细考虑；且 NC 的确认延迟对 DeFi 类场景是限制，
> 所以 PoB + BFT 也值得探索。这是目前尚未收敛的开放问题。

### 4.8 为什么不用 PoS + BFT（#1）

**经济层面**：PoS 起步成本低（印钞 + 云服务器即可），牛市早期能低成本反复拉盘；
但币价一旦下跌，信用和价格极难挽回，且拉盘严重依赖交易所和做市商，项目方容易被
牵着鼻子走。

**技术层面**：

- 各类 BFT（pBFT、HotStuff…）工程复杂度和调试难度都高，开源实现不易直接使用；
- BFT 网络传播复杂度高，且**主观性极强**（投票本身不是客观可验证的共识）；
- PoS 的安全性随币价下跌成倍衰减，restaking 之类的 DeFi 协议还会进一步透支它。

**PoB 相对 PoS 的额外好处（#6）**：矿工与项目方**直接建立联系**。传统 PoS 里，
项目方发币 → 用户去交易所买 → 再质押，中间被交易所割两刀，项目方拿不到足够现金流，
用户买到的 token 还得质押成没有流动性的死钱、随时承担跌价风险。PoB 里矿工的钱
直接到项目方，而矿工拿到的 L2 native token 是**有流动性的活钱**，可以立刻拿去做
任何事。

### 4.9 这不是赌博（#5）

竞拍失败的矿工**也会拿到一定额度的 L2 native token 作为补偿**，类似 ETH 对叔块
出块者的补偿。所以它不是「赌赢得记账权、赌输币归零」的零和博弈。

同时它也不是吸血 L1，而是给 L1 抬轿子的正循环：

```
   L2 应用价值提升
        │
        ▼
   L2 gas fee 提高 → L2 native token 更值钱
        │
        ▼
   更多 CKB holder 愿意支付 CKB 去做 L2 矿工
        │
        ▼
   CKB 买压增加 → CKB 更值钱  ──┐
        │                       │
        └───────────────────────┘

   反之：L2 是垃圾应用链 → native token 不值钱 → 没人愿意拿 CKB 来挖 → 自然出清
```

> #14（janx）补充了 PoB 与 ICO 的区别：PoB 的交易发生在 **L2 上线之后**（技术风险
> 已部分兑现）、**必须出钱又出力**（只出钱进不了一级市场）、且是**长期机制**
> （利于价格发现和广泛分发，而非 FOMO 与垄断）。

### 4.10 为什么不烧掉 L1 代币（#29）

前提：PoB 希望**大量应用链**都能作为 L2 挂在 L1 上，所以要考虑的是**可大规模、
可持续**地使用。在这个前提下烧币会有三个后果：

1. **燃烧速度 > L1 增发速度**：本质是在消灭 L1 的财富，L1 面临流动性枯竭甚至消亡；
2. **燃烧速度 ≤ L1 增发速度**：本质是再分配。那就必须回答「这些增发回来的币该给谁」
   —— 而 PoB 直接把币转给一个固定地址（L2 基金会），本身就是这种再分配的一个特例；
3. 通缩推高币价后，持币者越来越不愿意把币烧给 L2，**L2 的共识安全成本反而越来越低**。

所以钱不烧，而是流向 L2 项目方，并且（#19）这些 CKB **不会被永久锁定**，它们是
流动的，会被用于支付 L2 团队的开发和运营成本。

### 4.11 项目方的女巫攻击与解法（#29 → #32）

不烧币直接引出一个问题：mining addr 一直在吸纳 L1 代币，项目方**几乎可以零成本
作恶** —— 它自己下场挖矿，钱是付给自己的，除了 L1 手续费之外没有成本，而其他矿工
还在源源不断地给它送钱。

VRF 只能保证「钱多不一定挖得到」，但挡不住**女巫攻击**：项目方可以化身 5000 个矿工
去和 10 个正常矿工抢出块权，把正常矿工的中奖概率无限稀释。

**解法：给流入 mining addr 的 CKB 打上不可逆的标记。**

```
     矿工支付 CKB ──────────────▶  mining addr
                                       │
                        转出时 type_script 注入一条规则:
                        「这些 token 永远不可以再回到 mining addr」
                                       │
              ┌────────────────────────┴────────────────────────┐
              ▼                                                 ▼
    ✅ 可以用来做别的事                            ❌ 无法再拿去挖自己的矿
       （发工资、资助生态）                            （女巫攻击被掐断）
```

- 规则写死在 `type_script` 里，项目方**无法用混币器等手段抹掉交易历史**来绕过；
- 唯一的绕过路径是拿被标记的 CKB 去市场上换普通 CKB。但被标记的 CKB 用途受限，
  兑换率普遍会**高于 1:1**，项目方必须付出超量的标记 CKB 才能换回可用于攻击的
  普通 CKB —— 这是不可持续的。而且 **L2 越值钱，兑换率越高，女巫攻击成本越大**。

## 5. 完整状态机（单个 L2 高度 h 的生命周期）

```
   [PRE-PAID]                                  矿工在 T-24 个 CKB 块前，
   为高度 h 的支付承诺 Commit(a_h) 已在 L1 上   ←  以密文形式声明完毕
        │
        │  L2 到达高度 h
        ▼
   [PROPOSED]
   vrf = VRF_sk(prev_hash);  goal = f(a_h, vrf)
   区块 = {txns, txn_root, extra:(vrf, proof, a_h, zk_proof, goal), sig, pubkey}
   → P2P 广播
        │
        │  在 block_interval 内收集其他矿工的候选块
        ▼
   [VERIFIED]  逐个候选块检查：
        ① VRF proof 对 candidate.MinerPubkey 是否成立
        ② 支付身份是否绑定出块身份（payer.pubkey == miner.pubkey）
        ③ a_h 的 zk 分配证明是否成立（Σa ≤ A）
        ④ 重算 goal
        │
        ▼
   [ADOPTED]   本地采纳 max(goal) 的区块 → 执行交易 → 落库 → 状态 finalize
        │
        │  (header, goal) 上传 L1
        ▼
   [ANCHORED]  L1 上同高度可能有多个 fork 竞争
        │
        │  L1 合约裁定 max(goal)
        ▼
   [FINALIZED] 承载它的 L1 区块出块完成 → 该 L2 分支不可回滚
        │
        ▼
   [FOLLOWED]  L2 节点读回 L1 的裁定结果；若本地链与之不一致 → 回滚并切换
```

## 6. 当前实现对照（`chain/consensus/`）

代码把 PoB 拆成了这几个文件：

| 文件 | 职责 |
| --- | --- |
| `proof_of_buy.go` | yu tripod 主体：`StartBlock` 出块竞争、`EndBlock` 执行落库、`finalityWorker` L1 终局 |
| `vrf.go` | ECVRF-SECP256K1-SHA256-TAI，输入为 `prev_block_hash`，公钥即 `MinerPubkey` |
| `score.go` | `CalcBlockScore = payment × uint64(vrf_output[:8])`，即 `f = 乘法` |
| `consensus_data.go` | `(VRFResult, L1Payment, BlockScore)` 编码进 `block.Extra` |
| `l1_payment.go` | `POST /pay_l1_token` 申报入口 + `L1PaymentVerifier` 接口 + mock 实现 |
| `l1_submitter.go` | `L1HeaderSubmitter` 接口（提交区块头 / 轮询确认）+ mock 实现 |
| `config.go` | `block_interval=3000ms`、`min_payment=100`、`finality_period=10` 等 |

**已经对上协议的部分**

- `goal = payment × vrf` 的加权计算（§4.2）；
- VRF 密钥 = 出块密钥、验证时使用 `block.MinerPubkey`，杜绝 grinding 和冒领（§4.3）；
- 候选块必须通过「VRF 验证 → 支付与出块身份绑定 → L1 支付验证 → 重算分数」四道检查；
- 终局由 L1 驱动：`FinalizeBlock` 只入队，真正的 `Chain.Finalize` 要等
  `l1Submitter.IsConfirmed` 返回 true，且严格按高度顺序放行（§4.6 的雏形）。

**尚未实现的部分（按归属分两类）**
