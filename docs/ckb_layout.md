# CKB 链上布局

Proof of Buy 在 CKB 上只占用两种 cell。本文规定它们的结构与验证规则，规定 L2 侧
必须自己完成哪些验证，以及两边的接口如何对应。

协议本身见 [proof_of_buy.md](proof_of_buy.md)，本文只谈落到 CKB 上的形态。

## 0. 设计约束

三条性质决定了下面所有取舍，先列出来：

**一笔交易的全部内容，在打包之前就对 L1 出块者可见。** data 如此，witness 同样如此
——witness 是交易的一部分，出块者要验证签名就必须读到它。白皮书 §9.6 要求出价内容
在入块前不可见，这一条就把"放进 witness 让脚本验一下"这条路彻底堵死了：凡是脚本
读得到的，正在出块的那个 L1 矿工也读得到。**出价上链时只能是一串看不懂的承诺。**

**脚本是验证器，不是计算器。** type script 只能看到当前这笔交易的 inputs、outputs、
cell_deps、header_deps 和 witnesses。它不能遍历链上状态，也就不能"扫描所有出价并
选出最大的"。

这两条叠加起来的结论是确定的：**L1 既看不见出价的内容，也扫不到出价的全集，因此
它不可能裁定谁赢。** 裁定只能在 L2 侧做。本布局据此把 L1 的职责压到最小。

**cell 的容量是长期锁定的。** 1 CKB = 1 字节，且只有销毁 cell 才退还。因此 cell
里只放**必须由链上状态承载的**数据，其余一律留在交易里——交易永久存在于 L1 区块中，
可供任何人事后核验，只是后续脚本读不到它。

## 1. L1 在协议里干什么

两件事，仅此而已：

| | L1 做什么 | 谁来验 |
| --- | --- | --- |
| 预付与分配 | 托管预付款，记录每个高度的支付承诺，保证它一经写入不可更改 | CKB 合约（R3.x） |
| 出价提交 | 给一串 32 字节的承诺盖一个"它在第几号区块上"的时间戳 | 无人验，只存（R4.1） |

**L1 不验证 VRF，不验证 goal，不验证任何 zk 证明，也不裁定分叉。** 它提供的是两样
L2 自己给不了自己的东西：一份不可篡改、不可回溯修改的支付记录，以及一份主链的备份
——每个区块的承诺在当时就留在了 L1 上，事后补写不进去。后者正是识别"事后花钱造一条
更高得分的分叉"所需的证据。剩下的全部判断由 L2 节点完成，清单见第 5 节。

这与白皮书 §8.2 的分工是同一句话：L1 备份，L2 裁定。

## 2. cell 总览

```
┌─────────────────────────────────────────────────────────────────┐
│  预算 cell            每个矿工一个，长期存在                      │
│    预付总额 + 高度到支付承诺的表                                  │
│    ↑ 矿工在出块前写入，写入后不可改，是 PoB 成本的链上凭据         │
├─────────────────────────────────────────────────────────────────┤
│  提交 cell            每个矿工每个高度一个，短期存在               │
│    一串 32 字节的承诺，别的什么都没有                             │
│    ↑ 矿工出块后提交，高度尘埃落定后自行回收容量                    │
└─────────────────────────────────────────────────────────────────┘
```

没有锚点 cell，也没有结算交易。L1 不记录"结算到哪个高度"，因为它无从判断任何高度
的赢家；一个它算不出来的结论，写上去只会与 L2 节点独立算出的结果打架。

## 3. 预算 cell

矿工的预付款与分配计划。每个矿工一个，由矿工自己创建和维护。这是本布局里唯一有
实质规则的地方——白皮书 §7 的整套成本模型都压在它身上。

```
lock    矿工的 secp256k1 key（只有本人能改）
type    budget_type_script
data
    prepaid         u64                     预付总额，单位 shannon
    cleared_below   u32                     已清理到哪个 L2 高度
    allocations     [(u32, [32]byte)]       (L2 高度, Poseidon 支付承诺)
```

承诺是 `Poseidon(amount, random)`，与 L2 侧 `consensus.PoseidonCommit` 同一参数化。
链上不验证这个承诺的内容——它是给 L2 节点核对用的，L1 只保证它写下就不会变。

### 验证规则

**R3.1 已有条目不可修改，也不可删除。** 高度低于 `cleared_below` 的条目除外。

这一条是整个防后广播优势机制在链上的落点，也是这份布局里最不能省的一条。白皮书
§7.3 要求矿工必须先承诺支付额、再计算 VRF；若矿工能在算完 VRF、发现 goal 不够高
之后回头改大承诺，那个时序就失效了。链上只有这一处能强制它。

**R3.2 `cleared_below` 单调不减。**

**R3.3 新增条目的高度必须 ≥ `cleared_below`。** 与 R3.2 合起来，一个被清理掉的
高度永远无法重新写入——矿工不能删掉旧条目再换一个承诺补记上去。

**R3.4 `prepaid` 只增不减。** 追加预付是允许的，撤回不是。

`cleared_below` 取代了早前设想的锚点 cell。清理的目的只是回收容量，是矿工自己的
事，不需要一个全链唯一的高度水位来许可——而那样一个 cell，在没有链上结算的前提下
也没人有资格推进它。

### 总额明文，每个高度的出价是承诺

`prepaid` 是明文，`allocations` 里每个高度对应的只是一串 Poseidon 承诺。这与白皮书
§7.2 一致，也是 CKB 的形态使然：容量转移本就是公开的，一笔预付款有多少，链上谁都查
得到，藏不住也不必藏。

要藏的是**每个高度出多少**。竞争者若能提前知道你为某个高度出了多少，§7.3 的时序保护
就落空了；而只知道你的总预算，推不出你在任何一个具体高度上的出价。

代价是矿工的总投入规模对外可见。若将来连总额也要隐藏，需要 CKB 侧具备隐私转账能力，
属于另一个议题。

## 4. 提交 cell

矿工对某个 L2 高度的出价，以承诺形式提交。每个矿工每个高度一个，各建各的，互不
消耗——这样同一个 L1 区块内的并发提交不会相互冲突。

```
lock    矿工可支配的 secp256k1 key（随时可自行回收容量）
type    commit_type_script
data
    commitment   [32]byte    SHA256(l2_block_hash || random)
```

**承诺的内容只有 L2 区块哈希。** 哈希已经唯一确定了整个区块——高度、`goal`、VRF
输出、父链接、每一笔交易都在里面——再把其中几项单独塞进承诺，等于把同一件事承诺
两遍。揭示时给出 `(l2_block_hash, random)` 就够：拿到区块的人先核对开启值与链上
承诺相符，再核对区块与哈希相符。

**用 SHA256 而不是 Poseidon。** 这个承诺不进任何电路：链上只记录、不验证，揭示由
L2 节点把两个字节串拼起来哈希一次就能核对。Poseidon 的 zk 友好在这里没人用得上，
代价却要照付——它的输入是 BN254 域元素，32 字节的哈希塞不进去，就得拆成两半，两边
还要约定拆法一致、参数化一致。换成字节串哈希，这两个问题都不存在。

预算 cell 里的支付承诺是另一回事，仍然用 Poseidon（第 3 节）：那些开启值确实要进
预算上限证明的电路。

### 验证规则

**R4.1 data 恰好 32 字节。** 这是这个脚本的全部职责。

**R4.2 消耗不受 type script 约束。** 高度尘埃落定之后，矿工凭 lock 花掉这个 cell
取回容量。链上没有结算交易会来消耗它。

### 为什么一条实质规则都没有

data 里只有一串哈希，链上没有任何东西可供比对：承诺的开启值不在这笔交易里（在也
不行，见第 0 节第一条），预算 cell 里的支付承诺同样是密文，VRF 的输入是 L2 的父
区块哈希而 L1 不知道 L2 的链长什么样。**没有明文，就没有可验之物。**

这不是把验证省掉了，是把它挪到了唯一有能力做的地方。L2 节点手里有完整的 L2 链、
有矿工广播的开启值、有 L1 上的承诺与支付记录，三者对齐才是一次完整的验证；L1 只
持有其中一份，验不出什么有意义的结论。

代价是 L1 上出现无效承诺不要钱——谁都可以创建一个内容荒谬的提交 cell。这不构成
攻击：L2 节点在校验开启值时会拒绝它，而攻击者白付了一笔 L1 手续费和一份容量占用。

### 承诺藏住了什么，没藏住什么

藏住的是出价的内容。没藏住的是"某个地址提交了一笔东西"——交易的输入来自矿工自己的
钱包，出块者据此能推断提交者是谁；预算 cell 的 allocations 也公开写着谁在为哪些
高度备战。

所以这层防御挡住的是**按出价高低定向丢弃**，挡不住按身份定向丢弃。后者的代价高得
多：它要长期持续地针对同一批地址，而矿工换一批地址与资金来源就重新变得不可
辨认，被针对的又恰好是最容易察觉自己被针对的人。

## 5. L2 侧必须自己完成的验证

L1 交出来的只是"哪些承诺在第几号区块上"。把它变成"这个高度谁赢"，是 L2 节点的事。
早前设想放在合约里的那套规则，一条不少地落到这里。

### 揭示走 L2 网络

承诺入块之后，矿工在 L2 的 p2p 网络里广播开启值：

```
l2_block_hash, random                       打开 L1 上的区块承诺
amount, payment_random                       打开预算 cell 里的支付承诺
vrf_output, vrf_proof, miner_pubkey, block_sig, prev_hash
```

开启值从不上 L1。它必须与 L2 区块一起持久化，新节点同步时要能从对等节点一并取到
——丢了开启值，那个高度的赢家就无从复原。

### 校验清单

收到一组开启值，节点依次检查：

**V1 承诺存在且已入块。** 重算 `SHA256(l2_block_hash || random)`，必须等于 L1 上
某个提交 cell 的 data。记下它所在的 L1 区块号。

**V2 分支连续。** 这个区块必须挂在一条从分叉点起逐高度相接、中间没有缺口的链上。
缺一个高度，整条分支就失去参选资格——不能把各个高度上得分最高的区块挑出来拼成
一条自己的链。

**没有时间窗口这一说。** 承诺来得早晚不决定它算不算数：一笔迟到的承诺照样合法，
它只是形成了一条很短的分支，在累计得分上赢不了。用不着一条规则去挡它，理由见本节
末尾的「分叉选择与终局」。

**V3 支付承诺匹配。** 读该矿工预算 cell 在 `l2_height` 上的条目 `c`，要求
`Poseidon(amount, payment_random) == c`。

**V4 支付承诺写得够早。** 写入 `c` 的那笔 L1 交易，必须比**这个区块自己的承诺**所在
的 L1 区块早至少 24 个 L1 区块。这是白皮书 §7.3 的支付前移，链上的 R3.1 只保证条目
不可改，"改得够早"要在这里查。

**V5 VRF 有效。** 以 `miner_pubkey` 为公钥、`prev_hash` 为输入验证
`(vrf_output, vrf_proof)`。VRF 公钥就是出块公钥，矿工无法用一次性密钥碾出有利输出。

**V6 goal 正确。** `goal == f(amount, vrf_output)`，`f` 取乘法，`vrf_output` 前 8
字节按大端解释为 u64。即 `consensus.CalcBlockScore`。

**V7 身份一致。** 预算 cell 的 lock args、`miner_pubkey`、`block_sig` 的签名者是
同一把密钥。矿工不能拿别人的支付来为自己出价。

**V8 父链接属实。** `prev_hash` 必须是本节点认定的 `l2_height - 1` 的区块哈希。
这一项以前明确标注为"链上验不了"，现在整份清单都在链下，它与其他项没有区别了。

全部通过，这个区块才是它所在分叉上的合法一环。选哪条分叉、何时不可回滚，见下一节。

### 分叉选择与终局

**分叉选择：取累计 `goal` 最大且区块连续的分叉。**

```
  分叉 A   h ── h+1 ── h+2 ── h+3        Σgoal = 410  ◀── 主链
  分叉 B   h ── h+1 ──  ✗  ── h+3        有缺口，不参选
  分叉 C   h ── h+1 ── h+2               Σgoal = 260
```

连续不是修饰语。允许缺口，就等于允许攻击者从每个高度挑出自己得分最高的那块拼成
一条分支——而那些高度上他本来是输的。要求逐高度相接，他就必须为每一块都付钱。

累计得分完全相同时，取分叉点后第一个区块哈希字典序小者。概率极低，但需要一条确定
的断路规则，否则不同节点会各执一词。

**终局：主链上承诺已被埋够 N 个 L1 区块的前缀，不再接受任何重组**，哪怕对方声称有
更高的累计得分。N = 24，见第 7 节。

累计得分回答"现在跟谁"，L1 深度回答"什么时候不可逆"。前者随时可能因为出现一条更重
的分支而改变，后者一旦到达就钉死了——这正是 L1 在这套共识里提供的东西：一个不受 L2
内部博弈影响的客观时间深度。

迟到的翻案因此双重失效：没到终局深度，它得拿累计得分说话，而那意味着把之后每一个
高度都重新买一遍；过了终局深度，它连参与比较的资格都没有。

### 这样做付出了什么

**L1 的历史不再自证 L2 的历史。** 重放 CKB 只能得到一堆无法解读的哈希；要复原"哪
条链赢了"，必须同时拿到 L2 网络里的开启值。

好在攻击者能做的有限：承诺是绑定的，**没人能编造出一个与链上承诺相符的假开启值**，
所以伪造一段 L2 历史是不可能的。可能的只有**隐瞒**——只把一部分开启值给某个新同步
的节点，让它算出一条累计得分较低的主链。这要求攻击者是该节点唯一的数据来源；从多个
对等节点取数即可化解。白皮书 §8.3 的长程攻击防御因此基本成立，但成立的理由变了：
不是"主链写在 L1 上"，而是"L1 上的承诺让历史无法被改写，重写就得重新付一遍钱"。

这是弱主观性。它的边界见第 7 节。

## 6. L2 侧接口映射

`chain/consensus/` 中三个接口与本布局的对应关系。提交与终局两处已按本布局改完，
支付读取一处仍待改。

### L1PaymentVerifier

```go
FetchPrepayment(ctx, txHash, minerPubkey) (commitment string, err error)
FetchAllocation(ctx, txHash, minerPubkey, height) (commitment string, err error)
```

读该矿工的预算 cell，分别返回 `prepaid` 与 `allocations` 中 `height` 对应的承诺，
查不到返回 `ErrPaymentNotFound`。

> 两处要改：形参 `txHash`（预付交易哈希）应换成按 `minerPubkey` 定位预算 cell，
> `txHash` 随之取消；`FetchAllocation` 还要返回**写入该条目的 L1 区块号**，V4 要
> 用它判断支付承诺是否写得够早，现有签名表达不了。

### L1CommitmentSubmitter（已改）

```go
SubmitCommitment(ctx, commitment *BlockCommitment) (l1TxHash string, err error)
```

构造并发送提交交易：抽一个 32 字节随机数，用 `consensus.CommitBlockHash` 算
`SHA256(l2_block_hash || random)`，创建提交 cell。`BlockCommitment` 里只有这串承诺
会上链，高度字段仅供本地记账。交易里不带任何与出价有关的其他数据——带了就等于没做
这层防御。

`random` 必须落盘保存：它是开启承诺的唯一钥匙，丢了这一笔出价就作废，付出去的 L1
代币也换不回对应的出块权。实现落在 `store.Bids`，且**先写盘再提交**：反过来的话，
一次崩溃就会在 L1 上留下一个谁也打不开的承诺。重发走 `resubmitCommitment`，复用已
存的那份开启值——换一个随机数就等于把旧承诺彻底作废。

承诺入块后，矿工还要在 L2 网络广播第 5 节那组开启值。这是 p2p 层的动作，不属于这个
接口，但必须与提交严格配对：**提交了不揭示等于没出价，揭示了对不上承诺会被全网拒绝。**

```go
ConfirmedDepth(ctx, l1TxHash) (depth uint64, found bool, err error)
```

`get_transaction` 取状态与所在区块，`get_tip_block_number` 取链头，算出承诺被埋了
多深，终局条件是

```
depth >= N
```

基准是这个区块自己的承诺。主链上满足该条件的最长前缀即为 finalized，此后不再接受
任何重组。

**提升是不可逆的**（L2 侧一旦提升，暂存写入即落盘且无法撤销），因此这里必须要求
足够深度，而不是"进块即可"。

`found` 把"还不够深"与"根本不在链上"分开：前者等着就行，后者意味着提交从未落地或
随 L1 重组消失，只能重发。一个 bool 表达不了这个差别，所以返回值里单列一项。

### L1Verdict（已删除）

这个接口的名字与语义都不再成立——L1 不出裁定——所以它连同 `FetchVerdict`、
`CompareVerdict`、`followVerdict` 与"钉住 L1 指定区块"的那套状态一起删掉了。终局
改由上面的深度条件给出。

接替它的是一个读取接口，等分叉选择落地时再加：

```go
FetchCommitments(ctx, height) ([]AnchoredCommitment, error)
// AnchoredCommitment{ Commitment [32]byte; L1Block uint64 }
```

用 indexer 按 `commit_type_script` 扫出该高度的全部提交 cell，连同各自所在的 L1
区块号返回。没有窗口可以先行过滤——一个区块算不算数，取决于它所在的分叉能否在累计
得分上胜出，与它来得早晚无关。注意要覆盖**已被矿工回收的**提交 cell：它们不在 live
cell 集合里，得从创建它们的交易里读。

之后与 p2p 收到的开启值配对，走第 5 节的 V1~V8，再取累计得分最大的连续分叉。这段
逻辑与 `verifyCandidate` / `ConfirmPayment` 高度重合，实现时应复用而非重写。

## 7. 已定与待确认

### 已定

**L1 只存不验。** 链上没有 VRF 验证，没有 zk 验证，没有 Poseidon 计算，没有裁定。
理由见第 0 节与第 4 节。

**为链上验 VRF 准备的东西已全部删除。** Rust 的 ECVRF 验证（`ckb/vrf`）与配套的
cycle 度量程序（`ckb/bench`、`ckb/bench-std`）都是为"把 VRF 放上链"准备的。实测一次
验证约 7.6M cycles，相对主网 35 亿的区块上限不到 0.25%——这个数字曾是那个方案的可行性
依据，如今链上什么都不验，它不再约束任何设计决策。

一度想把 `ckb/vrf` 留作 L2 侧 Go prover 的对照实现，但那个理由站不住：交叉验证的价值
在于两个独立实现必须互操作，而链上不验之后没有谁需要与 Go 侧互操作，所有 L2 节点跑的
是同一份代码。它检验的东西不是任何人依赖的东西，所以一并删了。L2 出块自己要用的 VRF
在 `chain/consensus/vrf.go`，与链上无关。

**容量占用是 O(1)。** 预算 cell 按 R3.1/R3.2 清理，提交 cell 由矿工自行回收，链上
没有任何随高度累积的长期状态。

**N = 24，终局深度，也是这里唯一的时间参数。** 主链上承诺被埋够 24 个 L1 区块的
前缀视为 finalized。

```
一个区块的承诺入块 ──── N = 24 个 L1 区块 ────▶ 该区块 finalized
                     L2 终局 ≈ 24 个 CKB 区块 ≈ 4 分钟
                     暂存层需压住约 80 个 L2 区块的写入
```

**没有"竞争窗口"一类的参数。** 分叉选择比的是累计得分，迟到的提交自己就赢不了，
不需要一条时限规则把它挡在外面。少一个参数，也就少一处各节点可能算出不同结果的
地方。

24 这个深度是给 L1 自身的重组留余量：低于它，"承诺已在链上"这件事本身还可能被推翻。
它应为配置项。

白皮书 §9.3 的 24 是另一个数：那是支付承诺要比自己这个区块的承诺提前多久（V4）。
两者各管各的，只是碰巧取了同一个值。

### 待确认

- **开启值的传播与留存。** 它现在是共识的必需品而非附属信息：新节点同步时必须能连
  同区块一起拿到历史开启值。要定的是它放在 L2 区块的哪个位置、由谁负责补发，以及
  一个矿工提交了却迟迟不揭示时，那笔承诺如何被当作弃权处理。
- **L1 重组与终局深度的叠加。** 一个区块的承诺所在的 L1 区块若被重组掉，它就退回
  "未上链"的状态，其所在分叉的合法性随之改变。N = 24 本就是为此留的余量，但边界
  需要确认：重组深度接近 N 时，不同节点会不会短暂地算出不同的主链。
- **弱主观性的边界。** 攻击者无法伪造开启值，只能隐瞒。需要量化：一个新节点要连到
  几个诚实对等节点才足够安全，以及是否值得提供一个可选的检查点机制。
- **无效承诺的成本。** 链上不验，创建一个垃圾提交 cell 只需手续费与可退还的容量。
  正常情况下无害，但需要估算它作为 L1 状态膨胀手段的成本下界。
