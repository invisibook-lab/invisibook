# CKB 链上布局

Proof of Buy 在 CKB 上只占用两种 cell。本文规定它们的结构与验证规则，规定 L2 侧
必须自己完成哪些验证，以及两边的接口如何对应。

协议本身见 [proof_of_buy.md](proof_of_buy.md)，本文只谈落到 CKB 上的形态。

## 0. 设计约束

三条性质决定了下面所有取舍，先列出来：

**一笔交易的全部内容都是公开的。** data 如此，witness 同样如此——witness 是交易的
一部分，出块者要验证签名就必须读到它，上链之后任何人都读得到。白皮书 §7.2 要求每个
高度的出价额在被用到之前不可见，这一条就把"放进 witness 让脚本验一下"这条路彻底堵死
了：凡是脚本读得到的，竞争者也读得到。**每个高度的出价上链时只能是一串看不懂的承诺。**

**脚本是验证器，不是计算器。** type script 只能看到当前这笔交易的 inputs、outputs、
cell_deps、header_deps 和 witnesses。它不能遍历链上状态，也就不能"扫描所有出价并
选出最大的"。

这两条叠加起来的结论是确定的：**L1 既看不见每个高度的出价，也扫不到出价的全集，因此
它不可能裁定谁赢。** 裁定只能在 L2 侧做。本布局据此把 L1 的职责压到最小。

**cell 的容量是长期锁定的。** 1 CKB = 1 字节，且只有销毁 cell 才退还。因此 cell
里只放**必须由链上状态承载的**数据，其余一律留在交易里——交易永久存在于 L1 区块中，
可供任何人事后核验，只是后续脚本读不到它。

## 1. L1 在协议里干什么

两件事，仅此而已：

| | L1 做什么 | 谁来验 |
| --- | --- | --- |
| 预付与分配 | 托管预付款，记录每个高度的支付承诺，保证它一经写入不可更改 | CKB 合约（R3.x） |
| 区块头提交 | 记录 L2 区块头，并给它盖一个"它在第几号区块上"的时间戳 | 只查长度，只存（R5.1） |

**L1 不验证 VRF，不验证 goal，也不裁定分叉；链上唯一验证的 zk 证明是预算 cell 的配平证明
（R3.2）。** 它提供的是两样 L2 自己给不了自己的东西：一份不可篡改、不可回溯修改的
支付记录，以及一份主链的备份——
每个区块的区块头在当时就留在了 L1 上，事后补写不进去。后者正是识别"事后花钱造一条
更高得分的分叉"所需的证据。剩下的全部判断由 L2 节点完成，清单见第 6 节。

这与白皮书 §8.2 的分工是同一句话：L1 备份，L2 裁定。

## 2. cell 总览

```
┌─────────────────────────────────────────────────────────────────┐
│  预算 cell            每个矿工一个，长期存在                      │
│    预付总额 + 高度到支付承诺的表                                  │
│    ↑ 矿工在出块前写入，写入后不可改，是 PoB 成本的链上凭据         │
├─────────────────────────────────────────────────────────────────┤
│  提交 cell            每次提交一个，短期存在                       │
│    一个明文的 L2 区块头                                           │
│    ↑ 区块产出后提交，高度尘埃落定后由提交者回收容量                │
├─────────────────────────────────────────────────────────────────┤
│  mining addr cell     全链唯一，长期存在，矿工的付款流入此处       │
│    带 mining_addr_type_script，钱流出时强制打标记                 │
│    ↑ 付款进来不受限，往外花才受约束                               │
├─────────────────────────────────────────────────────────────────┤
│  已用代币 cell        项目方从 mining addr 支出时产生，永久携带    │
│    与普通代币的唯一区别：带着一个洗不掉的类型脚本                  │
│    ↑ 流出 mining addr 时打上，此后永远回不去                      │
└─────────────────────────────────────────────────────────────────┘
```

没有锚点 cell，也没有结算交易。L1 不记录"结算到哪个高度"，因为它无从判断任何高度
的赢家；一个它算不出来的结论，写上去只会与 L2 节点独立算出的结果打架。

## 3. 预算 cell

矿工的预付款与分配计划。每个矿工一个，由矿工自己创建和维护。这是本布局里唯一有
实质规则的地方——白皮书 §7 的整套成本模型都压在它身上。

```
lock    secp256k1_blake160_sighash_all，args = blake160(矿工出块公钥)（R3.5）
type    budget_type_script
data
    prepaid       u64                     预付总额，单位 shannon
    allocations   [(u32, [32]byte)]       (L2 高度, Poseidon2 支付承诺)
witness
    budget_proof  STARK（Plonky3）         证明所有 amount 之和恰好等于 prepaid，
                                          按 32 KB 切块放在连续的几个 witness 里
```

承诺是 KoalaBear 域上宽度 16 的 Poseidon2，截取输出的前 8 个域元素：

```
  Poseidon2( amount 的 4 个 16 位分段（小端）‖ random 的 8 个域元素 ‖ 0,0,0,0 )[0..8]
```

编码成 32 字节时，每个域元素写成一个 u32 小端。它与 L2 侧 `consensus.PaymentCommit`、
证明电路 `lib/budget-stark` 逐字节一致。链上不打开这个承诺——它是给 L2 节点核对用的——
但链上**要验证那个 zk 证明**，见 R3.2。

承诺选 Poseidon2 而不是别的哈希，是因为它要进证明的电路：STARK 在 KoalaBear 这种 31 位
小域上运算，Poseidon2 是这个域上的原生哈希，电路代价最低。

### data 的字节布局

```
  偏移   长度   内容
  0      8      prepaid            u64 小端
  8      4      分配表条目数        u32 小端      ┐ molecule fixvec
  12     36×n   条目               见下           ┘

  一个条目（molecule struct，定长 36 字节）
  +0     4      height             u32 小端
  +4     32     commitment         Poseidon2 承诺，8 个 u32 小端，
                                   每个都必须小于 KoalaBear 的模数
```

**`prepaid` 在 molecule 之外，是刻意的。** `budget_type_script` 每创建一个预算 cell
都要读一次总额（R3.3），把它放在最前面的裸 8 字节，脚本一次定长读取就拿到；包进
molecule table 的话，那 8 字节会变成 table 自己的长度与偏移头，脚本得先解析容器才能
取到它要的唯一一个字段。

**分配表用 molecule。** 它是这份 data 里唯一长度可变的部分，条目数写在头里，读的一方
无需按剩余字节倒推，长度对不上即判定这个 cell 不是它自称的形状。条目定长，所以用
fixvec——molecule 为变长向量准备的偏移表在这里是纯开销。

**条目按 height 升序，且不得重复。** 重复意味着同一个高度挂着两个承诺，而没有任何规则
可以在两者之间做选择；升序则让读的一方遇到第一个大于目标的高度就能停。编码与解码两侧
都强制这一条：表一次写定、永不可改（R3.1），编错就是一笔预付款白白扔掉。

Go 侧的编解码在 `chain/ckb/budget_data.go`。

**一张表一次写定，此后整个 cell 不可变。** 分配不是逐条追加的：矿工预付多少，就在创建
这个 cell 时一次性把它分配干净。想追加预算，就再建一个预算 cell，各自带各自配平的表。

### 验证规则

**R3.1 创建之后，cell 的 data 不可修改。** 预算 cell 只有两种合法转移：被创建，或者
被矿工用自己的 lock 整个花掉回收容量。没有"改一改"这种中间状态。

这一条是防后广播优势机制在链上的落点。白皮书 §7.3 要求矿工必须先承诺支付额、再计算
VRF；若矿工能在算完 VRF、发现 goal 不够高之后回头改大承诺，那个时序就失效了。链上
只有这一处能强制它。

**R3.2 分配必须配平：`Σ amount == prepaid`。** 创建时，脚本从 witness 里取出证明并
验证它，通不过这个 cell 就不能存在。证明对**表里的每一个承诺、它们的顺序和条目数**
都有约束，任何一项被改动都验证不过。

取等式而非"不超过"，是因为语义更干净：钱已经真的付给 mining addr 了，"没分配完的
部分"并不会退回来，声明它的去向本就是矿工自己的事。

证明**不能**省掉对每个 `amount` 的范围约束：证明所在的域会回绕，不约束大小的话，一个
"负数"额度（模 p 意义下）就能把别的高度撑大，而那个"负数"高度矿工永远不会去揭示，
V3 也就查不到它。所以电路把每个 `amount` 拆成 64 个比特，保证它是真正的 u64。

证明系统是 Plonky3 的单变量 STARK，建在 KoalaBear 域上，承诺方案是零知识的 FRI，
Merkle 树与 Fiat-Shamir 用 Keccak。它是透明的：不需要任何可信设置，验证密钥由电路
形状确定。安全参数为 FRI 扩展倍数 16、查询 24 次、查询前工作量证明 20 bit，按 Plonky3
自带的估算，推测安全性 103 bit，可证明安全性 67 bit。

电路（`lib/budget-stark/src/air.rs`）每行对应表里一个条目，约束三件事：

- 该行的承诺确实是 `Poseidon2(amount, random)`，且 `amount` 是 u64；
- 各行承诺依次串成一条哈希链 `acc_{i+1} = Poseidon2(acc_i ‖ c_i)`，最后一行的 `acc`
  作为公开值。脚本用原生代码对链上那张表重算同一条链，两者相等，表就被逐项绑住了；
- 各行金额的 4 个 16 位分段分别累加，最后一行带进位规整后等于 `prepaid` 的 4 个分段。

表不足 128 条时补齐到 128 行（零知识要求 trace 至少这么高），补的行金额为 0、随机数
为 0。一张表最多 1024 条。

**证明放在哪里。** 证明约 110 KB，不能整块放进一个 witness：矿工自己的标准 sighash
lock 签名时会把它覆盖的每个 witness 读进 32 KB 的缓冲区，更大的就报错。所以证明前面
加上 4 字节的总长度（u32 小端），按每块不超过 32 KB 切开，从预算 cell 在交易中的
output 下标开始，依次放进连续几个 witness 的 `WitnessArgs.output_type`。脚本先找到
自己的 output 下标，再逐个读取、拼接，长度对不上就拒绝。格式定义在
`lib/budget-stark/src/witness.rs`，Go 侧对应 `chain/ckb/budget.go` 的 `proofWitnesses`。

这与第 0 节"witness 对出块者可见"并不冲突：证明是零知识的，读到它也得不到任何一个
高度的额度。

**代价。** 表不超过 128 条时，验证约 4900 万 cycle，约占一个区块上限（35 亿）的 1.4%；
1024 条时约 8900 万。交易约 114 KB，手续费按体积计，最低费率下约 0.0012 CKB。脚本
二进制去掉符号表后约 217 KB，部署时按字节锁定容量。

**R3.3 `prepaid` 必须等于同一笔交易中转入 mining addr 的容量。** 创建预算 cell 的
那笔交易里，要有一个 lock 等于 mining addr 的输出，其 capacity 恰好是 `prepaid`。
写一个比实际付款大的数就等于凭空印钱。

**钱不留在预算 cell 里。** 这一点容易看错。矿工付款的去向是 mining addr（第 4 节的
资金流第一段），预算 cell 只存那张表；它自己的 capacity 是占用链上存储所要锁定的
容量，连同这笔交易的手续费，都是矿工在 `prepaid` 之外自行承担的链上成本——押金在
把 cell 花掉时收得回来（R3.1），手续费付给 CKB 矿工。把这两者与 `prepaid` 混为一谈，
就会以为钱锁在 cell 里，而它早已不可追回。

**R3.4 预付款不得来自已用代币。** 交易的 inputs 里不能有带 `spent_type_script` 的
cell（见第 4 节）。少了这一条，第 4 节的整套标记形同虚设：项目方把代币从 mining addr
花出去、打上标记，转头就能拿这些被标记的代币来写自己的预算 cell 继续挖矿。

**R3.5 lock 必须是标准 sighash lock。** 预算 cell 的 lock 只能是
`secp256k1_blake160_sighash_all`，其 args 是所有者公钥的 blake160。

这一条是第 6 节 V7 第一项的前提。那一项要求 L2 区块的 `miner_pubkey` 与这个 cell 的
所有者是同一把密钥；若 lock 的形式不固定——换成多签，或某个自定义脚本——args 里根本
不存在"单一公钥"这回事，"同一把密钥"也就没有可比对的落点。

**链上只能管到形式，管不了身份。** CKB 看不见 L2 区块，不知道出块公钥是谁，所以
"args 是否等于 `blake160(miner_pubkey)`"只能由 L2 节点去比。链上把 lock 的形式定死，
链下那一比才成立——两边缺一不可。

要绑的是**这张表归谁用**，不是谁付的钱。出钱的可以另有其人：A 自愿掏钱、把预算 cell
的 lock 设成 B 的，那是 A 的授权；冒领指的是 B 拿 A 的表去出块，而那由 lock 挡住。

早前设想过一个 `cleared_below` 水位，用来清理已经用过的旧条目。`== prepaid` 之下它
没有存在理由了：整张表一次写定、永不修改，"清理"只剩把整个 cell 花掉这一种形式，
而那由 lock 管就够了。

### 总额明文，每个高度的出价是承诺

`prepaid` 是明文，`allocations` 里每个高度对应的只是一串 Poseidon2 承诺。这与白皮书
§7.2 一致，也是 CKB 的形态使然：容量转移本就是公开的，一笔预付款有多少，链上谁都查
得到，藏不住也不必藏。

要藏的是**每个高度出多少**。竞争者若能提前知道你为某个高度出了多少，§7.3 的时序保护
就落空了；而只知道你的总预算，推不出你在任何一个具体高度上的出价。

代价是矿工的总投入规模对外可见。若将来连总额也要隐藏，需要 CKB 侧具备隐私转账能力，
属于另一个议题。

## 4. 已用代币 cell

白皮书 §9.4 的落点。mining addr 持续吸纳矿工付来的代币，这让项目方处在一个特殊位置：
它自己挖矿时，钱是付给自己的，除 L1 手续费外没有真实成本，而 VRF 挡不住它化身几千个
矿工把诚实矿工的中选概率稀释掉。

防御不是禁止项目方花钱，而是**给花出去的钱打上洗不掉的标记，让它再也回不到 mining
addr**：

```
  矿工支付 ────▶  mining addr（干净）
                        │
                   项目方支出
                        │
                        ▼
                 已用代币 cell（带 spent_type_script）
                        │
            ┌───────────┴───────────┐
            ▼                       ▼
     开发、运营、生态资助      回不去 mining addr，
                              也写不了预算 cell
```

```
lock    任意（花给谁就是谁的）
type    spent_type_script
data    空
```

### 验证规则

**R4.0 流出 mining addr 必须打标记。** 由 `mining_addr_type_script` 守在 mining addr
的 cell 上：消耗它时，每个 output 要么带 `spent_type_script`，要么仍是 mining addr
自己（后者是找零，钱没真正离开）。

这一条是标记的**来源**，没有它下面两条都落空——R4.1 与 R4.2 管的都是"标记已经存在
之后"，而 mining addr 若只是个普通 lock，项目方拿私钥一签、输出一个干净 cell，那两条
规则一条也碰不到。整套防御会被一个签名绕过去。

因此 mining addr 必须从一开始就带上这个 type script。矿工付款进来不受任何限制（钱是
干净的），规则只在往外花的那一刻生效。

**R4.1 标记只增不减。** 任何消耗已用代币 cell 的交易，其 outputs 中**每一个**
capacity 有来源于该 input 的 cell，都必须同样带上 `spent_type_script`。

这一条是标记"洗不掉"的全部依据。少了它，项目方付给 A、A 再付给 B，两手之后标记就没
了。要求它向所有后继传播，才堵得住这条路——白皮书说的"无法通过混币等抹除交易历史的
手段绕过"，指的就是这个。

**R4.2 不得流回 mining addr。** outputs 中不能有 lock 等于 mining addr 的 cell。

**R4.3 不得用于预付。** 由 R3.4 在预算 cell 那一侧强制，这里不重复检查——预算 cell
的脚本本来就要遍历自己的 inputs，让它顺手看一眼比在这里反向追踪便宜得多。

### mining addr 写在哪里

`spent_type_script` 要判断"是不是流回了 mining addr"，就得认得这个地址。它作为
`args` 传进脚本，而不是硬编码在代码里——同一份脚本代码因此可以服务多条 L2 链，各自
用不同的 args 部署。

代价是这个 args 一经部署就不能改：改了就是另一个脚本、另一份标记，旧标记管不住新
地址。**mining addr 因此是一次性选定、终身不可更换的。** 这一点要在上线前想清楚，
它比看上去更重。

### 这条防御的边界

链上能做的到此为止：代币被标记、回不去、用不了预付。剩下的是市场行为——项目方可以
拿被标记的代币去市场上换普通代币。白皮书 §9.4 论证过这条路不可持续：被标记代币用途
受限，兑换率普遍高于一比一，且 L2 越有价值兑换率越高。链上机制不试图禁止兑换，只负责
让它必须发生在链下、且必须付出溢价。

## 5. 提交 cell

一个 L2 区块的区块头，明文上链。每次提交一个，各建各的，互不消耗——这样同一个 L1
区块内的并发提交不会相互冲突。

```
lock    提交者可支配的 secp256k1 key（随时可自行回收容量）
type    commit_type_script
data
    header       bytes       L2 区块头，yu 的 protobuf 编码，不超过 4096 字节
```

**放整个区块头，而不只是区块哈希。** 区块头里有高度、父链接、出块公钥与签名，以及
Extra 里的 VRF 输出、证明和支付开启值。放整个区块头，L1 就是一份自足的记录：读 L1
的人自己重算区块哈希（`consensus.ComputeBlockHash`，对去掉 Hash 与签名后的区块头取
SHA256），就知道这条记录属于哪个 L2 区块，用不着任何人另行告知；`goal` 也能直接从
区块头里算出来。只放哈希的话，节点还得另外拿到区块，才知道这串哈希代表什么。

**哈希重算，不照抄。** 区块头自带一个 Hash 字段，但节点从不采信它：谁都可以写一个
提交 cell，一个自称是区块 X、内容却不是 X 的区块头，按重算的哈希它就落不到 X 头上。

**谁都可以提交。** 提交不要求身份（白皮书 §8.1）：区块头由出块者签名，提交者改不了
其中任何一项。同一个区块因此可能有多笔提交，节点取窗口内最早入块的那一笔作为它的
锚定高度。

**只在所属窗口内算数。** 第 `i` 批 L2 高度的区块头必须落在 L1 的 `[n+i, n+i+k]` 内
（白皮书 §8.1）。CKB 脚本读不到自己所在区块的高度，这一条链上管不了，由 L2 节点在读取
时按窗口过滤。

### 验证规则

**R5.1 data 非空，且不超过 4096 字节。** 这是这个脚本的全部职责。上限与 L2 侧的
`consensus.MaxHeaderLen` 一致；一个 PoB 区块头远小于这个数，上限只是不让提交 cell
被拿去在 L1 上存放任意大的数据。

**R5.2 消耗不受 type script 约束。** 高度尘埃落定之后，提交者凭 lock 花掉这个 cell
取回容量。链上没有结算交易会来消耗它。cell 花掉之后，区块头仍留在创建它的那笔交易
里，永久可查。

### 为什么链上不解码区块头

脚本不检查区块头的格式，更不检查它的内容。检查内容需要 L2 的整条链：父区块是哪个、
VRF 输入是什么、支付承诺在哪张预算表里，这些 L1 都不知道。只检查格式则要在合约里
实现 yu 的 protobuf 编码，换来的只是把一部分垃圾挡在链外——而垃圾本来就无害：节点
解码失败或重算出的哈希对不上任何区块，就当它不存在，攻击者白付了一笔 L1 手续费和
一份容量占用。

## 6. L2 侧必须自己完成的验证

L1 交出来的只是"哪些区块头在第几号区块上"。把它变成"这一批谁赢"，是 L2 节点的事。
早前设想放在合约里的那套规则，一条不少地落到这里。

### 按窗口从 L1 读

锚定的时间表是公开参数：L2 创世对应 L1 高度 `n`（写在创世区块头里，改了就是另一条
链），每批 `b` 个高度，第 `i` 批的窗口是 L1 `[n+i, n+i+k]`。节点据此直接算出一批该去 L1 的哪一段找，不需要任何 L2 网络消息，
也不需要维护跨批次的索引。

L1 到达 `n+i+k+d` 时，节点用 CKB indexer 按 `commit_type_script` 列出窗口内创建的
提交 cell（`block_range` 过滤），逐笔按交易哈希重新取一遍入块状态（只认已上链的），
解码其中的区块头。`d` 个确认之后窗口内容不再随重组变化，读完、裁定完，这一批的状态
全部可以丢掉。

### 校验清单

对窗口里读出的每个区块头，节点依次检查：

**V1 区块头在窗口内入块，且确为出块者所签。** 高度属于本批，所在 L1 区块在窗口内；
区块哈希由内容重算后等于区块头自称的哈希，且出块者对这个哈希的签名成立。同一区块头
有多笔提交时，取窗口内最早入块的那一笔。

记下该 L1 区块的高度：V4 拿它和支付承诺的写入高度比。

**V2 分支连续且整批齐全。** 这个区块必须挂在一条从上一批裁定结果起逐高度相接的链上，
且这条链覆盖本批全部 `b` 个高度。缺一个高度，整条分支就失去参选资格——不能把各个
高度上得分最高的区块挑出来拼成一条自己的链。

**V3 支付承诺匹配。** 读该矿工预算 cell 在 `l2_height` 上的条目 `c`，要求
`Poseidon2(amount, payment_random) == c`（`consensus.PaymentCommit`）。

表是否配平不用在这里查：配不平的预算 cell 根本上不了链（R3.2）。

**V4 支付承诺写得够早。** 写入 `c` 的那笔 L1 交易，必须比**这个区块自己的区块头**所在
的 L1 区块早至少 24 个 L1 区块。这是白皮书 §7.3 的支付前移，链上的 R3.1 只保证整张
表一经写定就不可改，"写得够早"要在这里查。

**V5 VRF 有效。** 以 `miner_pubkey` 为公钥、`prev_hash` 为输入验证
`(vrf_output, vrf_proof)`。VRF 公钥就是出块公钥，矿工无法用一次性密钥碾出有利输出。

**V6 goal 正确。** `goal == f(amount, vrf_output)`，`f` 取乘法，`vrf_output` 前 8
字节按大端解释为 u64。即 `consensus.CalcBlockScore`。

**V7 身份一致。** 预算 cell 的 lock args、`miner_pubkey`、`block_sig` 的签名者是
同一把密钥。矿工不能拿别人的支付来为自己出价。

比对方式是 `blake160(miner_pubkey) == 预算 cell 的 lock args`——CKB 标准 lock 的
args 是公钥的 blake160（20 字节），不是压缩公钥本身，与 `miner_pubkey` 和 `block_sig`
那两项直接比公钥不同。lock 的形式由 R3.1 那一节的 R3.5 定死，否则这一比无从下手。

**这一项是整套支付校验的地基，不是补充。** 少了它，V3 拿来比对的那个承诺就是矿工自己
给的：他编一个承诺，再配一套能打开它的 `(amount, payment_random)`，Poseidon2 照样对得
上，`amount` 随他写多大，`goal` 也就随之膨胀。V3 会退化成"自述与自述一致"。

**V8 父链接属实。** `prev_hash` 必须是同一分支上 `l2_height - 1` 的区块哈希，本批第
一块则必须接在上一批裁定结果的最后一块之后。
全部通过，这个区块才是它所在分叉上的合法一环。选哪条分叉、何时不可回滚，见下一节。

### 分叉选择与终局

**按批裁定，窗口关闭之后才裁。**

```
  L1   n+i ──────────── n+i+k ─────── n+i+k+d
        └── 第 i 批窗口 ──┘    确认深度    └─▶ 裁定第 i 批
```

L1 到达 `n+i+k+d` 时，节点读取第 `i` 批窗口内的全部区块头，丢掉过不了第 6 节校验的，
在剩下的里面**取接在第 `i-1` 批结果之后、整批齐全、逐块相连、累计 `goal` 最大的那条
分支**。实现见 `consensus.ChooseBatch`。

```
  分支 A   tip ── h ── h+1 ── h+2        Σgoal = 410  ◀── 主链
  分支 B   tip ── h ──  ✗  ── h+2        有缺口，不参选
  分支 C   tip ── h ── h+1               不齐全，不参选
```

整批齐全是参选资格，不是加分项。`k` 按链质量选取，诚实矿工完成的整批一定会在窗口
内入块，缺块的分支是网络没有完成的，不是输掉的。

累计得分完全相同时，取第一个分歧高度上区块哈希字典序小者。概率极低，但需要一条确定
的断路规则，否则不同节点会各执一词。

**裁定只读 L1。** 窗口内容在 `d` 个确认之后对所有节点都一样，每个节点在同一份数据上
做同一组校验，因此必然选出同一条分支，与它本地先跟了哪条分叉无关。选中的区块若还没
到达本节点，就等它同步过来再落盘。

**迟到的提交不算数。** 窗口一关，再提交上来的区块头落在窗口之外，根本不参与比较。
事后花钱造出来的分叉拿不出"当时就在窗口里"的区块头，详见白皮书 §8.2。

### L1 自证 L2 的历史

区块头明文上链，重放 CKB 就能得到每个高度上被锚定过的全部区块头、它们各自最早入块的
时间与 `goal`。分叉选择所需的一切都在 L1 上，新节点不依赖任何对等节点如实转述：
攻击者既伪造不了历史，也隐瞒不了历史。交易本体仍从对等节点取，由区块头里的交易根
约束。

## 7. L2 侧接口映射

`chain/consensus/` 中三个接口与本布局的对应关系。三者的 CKB 实现都在
`chain/ckb/`，由一个 `ckb.Client` 同时承担——在链上它们是同两种 cell 的三个视图，
拆成三份就是三条连接、三份脚本配置，以及三次让这些配置彼此走样的机会。

节点在 `[ckb] enabled = true` 时接上真实 CKB，否则退回内存里的 mock L1。脚本地址
逐链部署，由 `chain/cmd/ckb-deploy` 发布并打印整段配置。

### L1PaymentVerifier

```go
FetchAllocation(ctx, txHash, minerPubkey, height) (*Allocation, error)
```

读该矿工由 `txHash` 创建的那个预算 cell，返回 `allocations` 中 `height` 对应的
Poseidon2 承诺，以及写入这张表的 L1 区块高度（V4 从这里起算），查不到返回
`ErrPaymentNotFound`。

L2 节点不需要读 `prepaid`：表与总额是否配平，在 cell 上链时已由 R3.2 定死。

**`txHash` 不能省。** 一个矿工可以有多个预算 cell——想追加预算就再建一个（第 3
节）——只凭 `minerPubkey` 定位不唯一，`txHash` 指明用的是哪一笔预付。

**V7 的第一项在这里落实。** `minerPubkey` 不只是查询用的键：它会读出预算 cell 的
lock，确认它的 code hash 是标准 sighash lock（R3.5 给的前提），并比对 args 是否等于
`blake160(minerPubkey)`，不符即 `ErrPaymentNotFound`。少了这一步，V3 比对的承诺就是
矿工自己给的——他编一个承诺、配一套能打开它的 `(amount, payment_random)`，Poseidon2
照样对得上，`amount` 随他写多大——整条支付校验退化成自证。

### L1HeaderSubmitter

```go
SubmitHeader(ctx, header *types.Header) (l1TxHash string, err error)
```

构造并发送提交交易：用 `consensus.EncodeHeader` 编码区块头，创建提交 cell。超过
4096 字节的区块头在这里就被拒绝，不必等脚本拒绝。

提交的时机由节点控制：区块头要等所属窗口打开（L1 tip + 1 ≥ `n+i`）才发出，早发会落在
窗口之前，谁也不看；窗口已经关闭的则不再提交。L2 跑在 L1 前面时，区块头就在本地排队。

```go
HeaderOnChain(ctx, l1TxHash) (bool, error)
```

`get_transaction` 取状态：已上链返回 true；还在交易池里返回包装了
`ErrSubmissionPending` 的错误；L1 不认识或已拒绝则返回 false。

false 只驱动一个决定：窗口未关就重发——提交要么从未落地，要么随 L1 重组消失了，从
这里看是同一回事，补救也是同一个。区块头由区块唯一确定，重发不需要保存任何额外状态。
还在池里的提交必须区别对待：重发会构造出一模一样的交易，被节点当作重复拒绝。

### L1Reader

```go
AnchoredIn(ctx, from, to uint64) ([]*AnchoredHeader, error)
// AnchoredHeader{ Header *types.Header; L1Height uint64 }
Tip(ctx) (uint64, error)
BudgetOwner(ctx, txHash) (args []byte, err error)
```

`AnchoredIn` 返回 L1 `[from, to]` 内创建的提交 cell 里能解码的全部区块头，各自带上
所在的 L1 高度，供第 6 节逐项校验。解码不了的 cell 直接跳过。

`Tip` 返回 L1 主链高度，用来判断窗口是否关闭、是否可以裁定。

`BudgetOwner` 返回预算 cell 的 lock args，供 V7 第一项比对。返回的是原始 args 而非
公钥：CKB 标准 lock 的 args 是公钥的 blake160，哈希在调用方那一侧算。


## 8. 已定与待确认

### 已定

**L1 只验预算配平，其余只存不验。** 预算 cell 创建时验证一个 STARK 证明（R3.2）；
提交 cell 只查长度（R5.1）；除此之外链上没有 VRF 验证，没有 goal 验证，没有裁定。
合约从不打开支付承诺：它只把表里的承诺串成哈希链交给证明去核对，承诺的开启由 L2
节点做（V3）。其余各项的理由见第 0 节与第 5 节。

**容量占用是 O(1)。** 一个预算周期结束后，矿工把整个预算 cell 花掉取回容量；提交 cell
同样由提交者自行回收。链上没有任何随高度累积的长期状态。

**终局按批、按窗口（第 6 节）。** 区块头必须落在所属批次的 L1 窗口里，这给区块盖上
"当时确实在"的时间戳，堵的是长程攻击；窗口关闭并确认之后，在窗口内整批齐全的分支里
取累计 `goal` 最大者。终局时间是确定的：第 `i` 批在 L1 到达 `n+i+k+d` 时裁定。

**时间参数。** 白皮书 §7.3 / §9.3 的 24 个 L1 区块：支付承诺要比用它出块的时刻提前
这么久（对应 V4），防的是从 L1 发起的自私挖矿。锚定时间表的 `n`、`b`、`k`、`d`
是配置项 `anchor_genesis_l1_height`、`anchor_batch_size`、`anchor_window`、
`anchor_confirm_depth`，默认 200、3、24、24：`k` 取链质量保证，`d` 取 L1 重组深度。
`n` 在定义创世区块时写进创世区块头，是创世哈希的一部分：配置了别的 `n` 的节点拒绝在
已有的链上启动，各节点不可能各用各的。

### 待确认

- **L1 重组把区块头带走之后。** 一个区块的区块头所在的 L1 区块若被重组掉，窗口未关时
  需要重发。要确认的是：节点在重发与重新计入之间如何保持一致。
- **`k` 与 `d` 的取值。** `k` 要保证任意连续 `k` 个 CKB 区块里必有一个愿意打包对手
  区块头的出块者，`d` 要覆盖 CKB 的实际重组深度。两者都要按 CKB 的出块权分布量化，
  它们同时决定终局延迟。
- **本地跟错分叉的节点。** 裁定选中的区块若本节点没有，要等同步过来才能落盘；节点
  本地若一直跟着另一条分叉，需要一条主动去取选中区块的路径。
- **无效提交的成本。** 链上只查长度，创建一个垃圾提交 cell 只需手续费与可退还的容量。
  正常情况下无害，但需要估算它作为 L1 状态膨胀手段的成本下界；节点读窗口时也要为
  每一个这样的 cell 读一次交易。
