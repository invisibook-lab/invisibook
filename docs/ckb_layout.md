# CKB 链上布局

Proof of Buy 在 CKB 上只占用两种 cell。本文规定它们的结构与验证规则，规定 L2 侧
必须自己完成哪些验证，以及两边的接口如何对应。

协议本身见 [proof_of_buy.md](proof_of_buy.md)，本文只谈落到 CKB 上的形态。

## 0. 设计约束

三条性质决定了下面所有取舍，先列出来：

**一笔交易的全部内容，在打包之前就对 L1 出块者可见。** data 如此，witness 同样如此
——witness 是交易的一部分，出块者要验证签名就必须读到它。白皮书 §9.6 要求出价内容
在入块前不可见，这一条就把"放进 witness 让脚本验一下"这条路彻底堵死了：凡是脚本
读得到的，审查者也读得到。**出价上链时只能是一串看不懂的承诺。**

**脚本是验证器，不是计算器。** type script 只能看到当前这笔交易的 inputs、outputs、
cell_deps、header_deps 和 witnesses。它不能遍历链上状态，也就不能"扫描所有出价并
选出最大的"。

这两条叠加起来的结论是确定的：**L1 既看不见出价的内容，也扫不到出价的全集，因此
它不可能裁定谁赢。** 裁定只能在 L2 侧做。本布局据此把 L1 的职责压到最小。

**cell 的容量是长期锁定的。** 1 CKB = 1 字节，且只有销毁 cell 才退还。因此 cell
里只放**必须由链上状态承载的**数据，其余一律留在交易里——交易永久存在于 L1 区块中，
可供任何人事后核验，只是后续脚本读不到它。

## 1. L1 在协议里干什么

两件事，仅此而已：

| | L1 做什么 | 谁来验 |
| --- | --- | --- |
| 预付与分配 | 托管预付款，记录每个高度的支付承诺，保证它一经写入不可更改 | CKB 合约（R3.x） |
| 出价提交 | 给一串 32 字节的承诺盖一个"它在第几号区块上"的时间戳 | 无人验，只存（R4.1） |

**L1 不验证 VRF，不验证 goal，不验证任何 zk 证明，也不裁定分叉。** 它提供的是两样
L2 自己给不了自己的东西：一份不可篡改、不可回溯修改的支付记录，以及一个无法被伪造
的时间顺序。剩下的全部判断由 L2 节点完成，清单见第 4 节。

这与白皮书 §8.2 的分工是同一句话：L1 定序，L2 裁定。

## 2. cell 总览

```
┌─────────────────────────────────────────────────────────────────┐
│  预算 cell            每个矿工一个，长期存在                      │
│    预付总额 + 高度到支付承诺的表                                  │
│    ↑ 矿工在出块前写入，写入后不可改，是 PoB 成本的链上凭据         │
├─────────────────────────────────────────────────────────────────┤
│  提交 cell            每个矿工每个高度一个，短期存在               │
│    一串 32 字节的承诺，别的什么都没有                             │
│    ↑ 矿工出块后提交，高度尘埃落定后自行回收容量                    │
└─────────────────────────────────────────────────────────────────┘
```

没有锚点 cell，也没有结算交易。L1 不记录"结算到哪个高度"，因为它无从判断任何高度
的赢家；一个它算不出来的结论，写上去只会与 L2 节点独立算出的结果打架。

## 3. 预算 cell

矿工的预付款与分配计划。每个矿工一个，由矿工自己创建和维护。这是本布局里唯一有
实质规则的地方——白皮书 §7 的整套成本模型都压在它身上。

```
lock    矿工的 secp256k1 key（只有本人能改）
type    budget_type_script
data
    prepaid         u64                     预付总额，单位 shannon
    cleared_below   u32                     已清理到哪个 L2 高度
    allocations     [(u32, [32]byte)]       (L2 高度, Poseidon 支付承诺)
```

承诺是 `Poseidon(amount, random)`，与 L2 侧 `consensus.PoseidonCommit` 同一参数化。
链上不验证这个承诺的内容——它是给 L2 节点核对用的，L1 只保证它写下就不会变。

### 验证规则

**R3.1 已有条目不可修改，也不可删除。** 高度低于 `cleared_below` 的条目除外。

这一条是整个防后广播优势机制在链上的落点，也是这份布局里最不能省的一条。白皮书
§7.3 要求矿工必须先承诺支付额、再计算 VRF；若矿工能在算完 VRF、发现 goal 不够高
之后回头改大承诺，那个时序就失效了。链上只有这一处能强制它。

**R3.2 `cleared_below` 单调不减。**

**R3.3 新增条目的高度必须 ≥ `cleared_below`。** 与 R3.2 合起来，一个被清理掉的
高度永远无法重新写入——矿工不能删掉旧条目再换一个承诺补记上去。

**R3.4 `prepaid` 只增不减。** 追加预付是允许的，撤回不是。

`cleared_below` 取代了早前设想的锚点 cell。清理的目的只是回收容量，是矿工自己的
事，不需要一个全链唯一的高度水位来许可——而那样一个 cell，在没有链上结算的前提下
也没人有资格推进它。

### 与白皮书的一处偏离

§7.2 要求预付总额本身也是密文承诺。CKB 的容量转移是公开的，无法直接表达"金额隐藏
的支付"，因此这里的 `prepaid` 是明文。

后果是矿工的**总预算**对外可见，但**每个高度的出价**仍然隐藏——而后者才是 §7.3
要保护的东西：竞争者无法提前知道你为某个高度出了多少。总预算泄露的信息要弱得多。

若将来要求总额也隐藏，需要 CKB 侧具备隐私转账能力，属于另一个议题。

## 4. 提交 cell

矿工对某个 L2 高度的出价，以承诺形式提交。每个矿工每个高度一个，各建各的，互不
消耗——这样同一个 L1 区块内的并发提交不会相互冲突。

```
lock    矿工可支配的 secp256k1 key（随时可自行回收容量）
type    commit_type_script
data
    commitment   [32]byte    Poseidon(l2_height, l2_block_hash, goal, random)
```

`l2_block_hash` 是 32 字节，`goal` 是 u128，都超出 BN254 的标量域，各拆成两个域
元素参与 Poseidon。拆法与 L2 侧 `consensus` 包必须一致，否则两边算出的承诺不同。

### 验证规则

**R4.1 data 恰好 32 字节。** 这是这个脚本的全部职责。

**R4.2 消耗不受 type script 约束。** 高度尘埃落定之后，矿工凭 lock 花掉这个 cell
取回容量。链上没有结算交易会来消耗它。

### 为什么一条实质规则都没有

data 里只有一串哈希，链上没有任何东西可供比对：承诺的开启值不在这笔交易里（在也
不行，见第 0 节第一条），预算 cell 里的支付承诺同样是密文，VRF 的输入是 L2 的父
区块哈希而 L1 不知道 L2 的链长什么样。**没有明文，就没有可验之物。**

这不是把验证省掉了，是把它挪到了唯一有能力做的地方。L2 节点手里有完整的 L2 链、
有矿工广播的开启值、有 L1 上的承诺与支付记录，三者对齐才是一次完整的验证；L1 只
持有其中一份，验不出什么有意义的结论。

代价是 L1 上出现无效承诺不要钱——谁都可以创建一个内容荒谬的提交 cell。这不构成
攻击：L2 节点在校验开启值时会拒绝它，而攻击者白付了一笔 L1 手续费和一份容量占用。

### 承诺藏住了什么，没藏住什么

藏住的是出价的内容。没藏住的是"某个地址提交了一笔东西"——交易的输入来自矿工自己的
钱包，出块者据此能推断提交者是谁；预算 cell 的 allocations 也公开写着谁在为哪些
高度备战。

所以这层防御挡住的是**按出价高低定向丢弃**，挡不住按身份定向丢弃。后者的代价高得
多：它要在整个窗口里持续针对同一批地址，而矿工换一批地址与资金来源就重新变得不可
辨认，被针对的又恰好是最容易察觉自己被针对的人。

## 5. L2 侧必须自己完成的验证

L1 交出来的只是"哪些承诺在第几号区块上"。把它变成"这个高度谁赢"，是 L2 节点的事。
早前设想放在合约里的那套规则，一条不少地落到这里。

### 揭示走 L2 网络

承诺入块之后，矿工在 L2 的 p2p 网络里广播开启值：

```
l2_height, l2_block_hash, goal, random      打开 L1 上的出价承诺
amount, payment_random                       打开预算 cell 里的支付承诺
vrf_output, vrf_proof, miner_pubkey, block_sig, prev_hash
```

开启值从不上 L1。它必须与 L2 区块一起持久化，新节点同步时要能从对等节点一并取到
——丢了开启值，那个高度的赢家就无从复原。

### 校验清单

收到一组开启值，节点依次检查：

**V1 承诺存在且已入块。** `Poseidon(l2_height, l2_block_hash, goal, random)` 必须
等于 L1 上某个提交 cell 的 data。记下它所在的 L1 区块号。

**V2 承诺赶在封盘之前。** 记 `first(h)` 为该高度**最早**那笔承诺所在的 L1 区块号，
则 `h` 的候选集是 L1 区块号落在 `[first(h), first(h) + N]` 内的全部承诺，N = 24，
超出的一律不算数。

这一条不能省。没有它，一个矿工可以按兵不动，一周之后再掏出一笔 goal 更高的承诺
——它的 goal 从一开始就被预算 cell 的分配与 VRF 钉死，伪造不了，但"什么时候把
承诺放上链"由它自己决定，按 `max(goal)` 全网就得回滚一周。**封盘点是终局存在的
前提。**

起点取自承诺自身，不需要任何"L2 高度 → L1 区块"的时间表：`first(h)` 是重放 L1 就
能算出的事实，空高度（无人出价）天然没有起点，也就没有窗口。抢跑起点的余地也很小
——一笔承诺要算数，其开启值必须过 V3~V8，其中 `prev_hash` 得是 `h-1` 的真实父块，
所以谁都无法在 `h-1` 出来之前就为 `h` 有效地开跑。

**V3 支付承诺匹配。** 读该矿工预算 cell 在 `l2_height` 上的条目 `c`，要求
`Poseidon(amount, payment_random) == c`。

**V4 支付承诺写得够早。** 写入 `c` 的那笔 L1 交易，必须比 `first(h)` 早至少 24 个
L1 区块。这是白皮书 §7.3 的支付前移，链上的 R3.1 只保证条目不可改，"改得够早"要
在这里查。

**V5 VRF 有效。** 以 `miner_pubkey` 为公钥、`prev_hash` 为输入验证
`(vrf_output, vrf_proof)`。VRF 公钥就是出块公钥，矿工无法用一次性密钥碾出有利输出。

**V6 goal 正确。** `goal == f(amount, vrf_output)`，`f` 取乘法，`vrf_output` 前 8
字节按大端解释为 u64。即 `consensus.CalcBlockScore`。

**V7 身份一致。** 预算 cell 的 lock args、`miner_pubkey`、`block_sig` 的签名者是
同一把密钥。矿工不能拿别人的支付来为自己出价。

**V8 父链接属实。** `prev_hash` 必须是本节点认定的 `l2_height - 1` 的区块哈希。
这一项以前明确标注为"链上验不了"，现在整份清单都在链下，它与其他项没有区别了。

全部通过，这个出价才进入 `l2_height` 的候选集。封盘后取 `max(goal)`，平手取
`l2_block_hash` 字典序小者——需要一条确定的断路规则，否则不同节点算出的赢家会不
一致。

### 终局来自哪里

不是来自某个 L1 合约的判决，而是来自**承诺集合的不可变性**：

```
承诺入块  ──▶  该 L1 区块被埋到足够深  ──▶  这个高度的候选集再也不会变
                                              │
                                              ▼
                                   所有诚实节点据同一集合算出同一个赢家
```

L1 给的是"这些、且只有这些承诺赶在了封盘之前"这一事实。事实一旦随 L1 区块定下来，
裁定就是一个纯函数，不需要投票，也不需要 L1 会算。

### 这样做付出了什么

**L1 的历史不再自证 L2 的历史。** 重放 CKB 只能得到一堆无法解读的哈希；要复原"哪
条链赢了"，必须同时拿到 L2 网络里的开启值。

好在攻击者能做的有限：承诺是绑定的，**没人能编造出一个与链上承诺相符的假开启值**，
所以伪造一段 L2 历史是不可能的。可能的只有**隐瞒**——只把一部分开启值给某个新同步
的节点，让它算出一个较低的赢家。这要求攻击者是该节点唯一的数据来源；从多个对等
节点取数即可化解。白皮书 §8.3 的长程攻击防御因此基本成立，但成立的理由变了：不是
"赢家写在 L1 上"，而是"L1 上的承诺让历史无法被改写"。

这是弱主观性。它的边界见第 7 节。

## 6. L2 侧接口映射

`chain/consensus/` 中三个接口与本布局的对应关系。三个都需要改。

### L1PaymentVerifier

```go
FetchPrepayment(ctx, txHash, minerPubkey) (commitment string, err error)
FetchAllocation(ctx, txHash, minerPubkey, height) (commitment string, err error)
```

读该矿工的预算 cell，分别返回 `prepaid` 与 `allocations` 中 `height` 对应的承诺，
查不到返回 `ErrPaymentNotFound`。

> 两处要改：形参 `txHash`（预付交易哈希）应换成按 `minerPubkey` 定位预算 cell，
> `txHash` 随之取消；`FetchAllocation` 还要返回**写入该条目的 L1 区块号**，V4 要
> 用它判断支付承诺是否写得够早，现有签名表达不了。

### L1HeaderSubmitter

```go
SubmitBlockHeader(ctx, header) (l1TxHash string, err error)
```

构造并发送提交交易：抽一个 32 字节随机数，算
`Poseidon(l2_height, l2_block_hash, goal, random)`，创建提交 cell。交易里不带任何
与出价有关的其他数据——带了就等于没做这层防御。

`random` 必须落盘保存：它是开启承诺的唯一钥匙，丢了这一笔出价就作废，付出去的 L1
代币也换不回对应的出块权。

承诺入块后，矿工还要在 L2 网络广播第 5 节那组开启值。这是 p2p 层的动作，不属于这个
接口，但必须与提交严格配对：**提交了不揭示等于没出价，揭示了对不上承诺会被全网拒绝。**

```go
IsConfirmed(ctx, l1TxHash) (bool, error)
```

`get_transaction` 取状态与所在区块，`get_tip_block_number` 取链头，要求

```
tip - first(h) >= N
```

基准是该高度**最早**那笔承诺，不是本节点自己那笔——这样每个节点算出的时刻相同。

**这一个条件同时管两件事**：候选集在此刻封盘（V2），本节点也在此刻落盘。两者本就
该是同一时刻——先落盘后封盘等于把已经写死的高度重新打开，先封盘后落盘则是白等。

**提升是不可逆的**（L2 侧一旦提升，暂存写入即落盘且无法撤销），因此这里必须要求
足够深度，而不是"进块即可"。

同时应区分"未确认"与"交易不存在"：后者意味着提交从未上链，需要重新提交，而现有
的 bool 返回值表达不了这个差别。

### L1Verdict

这个接口的名字与语义都不再成立：L1 不出裁定。它实际要做的是**读出一个高度的承诺
集合**，裁定由本地算：

```go
// 现在
FetchVerdict(ctx, l1TxHash) ([]CanonicalL2Block, error)

// 应改为，名字也该跟着换（L1CommitmentReader 之类）
FetchCommitments(ctx, height) ([]AnchoredCommitment, error)
// AnchoredCommitment{ Commitment [32]byte; L1Block uint64 }
```

用 indexer 按 `commit_type_script` 扫出 `[first(h), first(h) + N]` 内创建的提交
cell，连同各自所在的 L1 区块号返回。注意要覆盖**已被矿工回收的**提交 cell：它们不在 live cell 集合里，得从
创建它们的交易里读。

之后与 p2p 收到的开启值配对，走第 5 节的 V1~V8，取 `max(goal)`。这段逻辑与
`verifyCandidate` / `ConfirmPayment` 高度重合，实现时应复用而非重写。

## 7. 已定与待确认

### 已定

**L1 只存不验。** 链上没有 VRF 验证，没有 zk 验证，没有 Poseidon 计算，没有裁定。
理由见第 0 节与第 4 节。

**因此 `ckb/vrf` 不再是合约的一部分。** 它与 `ckb/bench`、`ckb/bench-std` 当初是为
在链上验 VRF 做的，那条路已经不走了。实测 7,618,328 cycles 的结论仍然有效，只是不再
构成约束。这份实现别删：它是 L2 侧 prover 的独立交叉验证，Go 与 Rust 两套实现对同
一组向量得出同一个 `beta`，这个价值与它跑在哪儿无关。

**容量占用是 O(1)。** 预算 cell 按 R3.1/R3.2 清理，提交 cell 由矿工自行回收，链上
没有任何随高度累积的长期状态。

**N = 24，而且只有这一个参数。** 高度 `h` 的封盘点是 `first(h) + N`：候选集在此刻
定死，节点也在此刻落盘。

```
h 的最早一笔承诺入块 ──── N = 24 个 L1 区块 ────▶ 封盘，同时落盘
                     L2 终局 ≈ 24 个 CKB 区块 ≈ 4 分钟
                     暂存层需压住约 80 个 L2 区块的写入
```

把"竞争窗口"与"确认深度"分成两个参数是很自然的写法，但那样它们会叠加，终局要
≈48 个区块。两者其实是同一件事的两面——候选集不再变化的那一刻，正是可以安全落盘
的那一刻——合成一个之后终局减半。

24 要同时够两个用途：给被机会主义审查丢掉的承诺留重试余量（CKB 的提名窗口约 2 个
区块，24 够重试十余次），以及给 L1 自身的重组留出概率确定性。它应为配置项。

白皮书 §9.3 的 24 是另一个数：那是支付承诺要比 `first(h)` 提前多久（V4）。两者各管
各的，只是碰巧取了同一个值。

### 待确认

- **开启值的传播与留存。** 它现在是共识的必需品而非附属信息：新节点同步时必须能连
  同区块一起拿到历史开启值。要定的是它放在 L2 区块的哪个位置、由谁负责补发，以及
  一个矿工提交了却迟迟不揭示时，那笔承诺如何在封盘时被当作弃权处理。
- **L1 重组与封盘的叠加。** `first(h)` 所在的 L1 区块若被重组掉，起点就要重算，
  候选集随之变化。N = 24 的深度本就是为此留的余量，但边界需要确认：重组深度接近 N
  时，不同节点会不会短暂地算出不同的 `first(h)`。
- **弱主观性的边界。** 攻击者无法伪造开启值，只能隐瞒。需要量化：一个新节点要连到
  几个诚实对等节点才足够安全，以及是否值得提供一个可选的检查点机制。
- **无效承诺的成本。** 链上不验，创建一个垃圾提交 cell 只需手续费与可退还的容量。
  正常情况下无害，但需要估算它作为 L1 状态膨胀手段的成本下界。
